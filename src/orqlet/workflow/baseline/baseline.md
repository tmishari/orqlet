## Orqlet baseline

These statements apply to every task in this repository. Orqlet writes them. A project may add to them and may never relax them. If a role's output contract or a phase restriction conflicts with the advice below, the contract and the restriction win. A role that only reports facts never proposes, recommends or refactors.

### How to work

- Do not guess. When a fact is not in the repository or in what you were told, write it down as a question and ask. An unknown stays unknown until a person answers.
- Keep facts and decisions apart. Research says what exists, with the file and line. Design and plan say what to change and why.
- Follow the conventions and the compatibility of this code base first. Add a pattern only when you can say which problem it solves here.
- Keep business rules independent of frameworks and I/O. Dependencies point from outer layers toward the domain, never the other way.
- Prefer the simplest design that meets the stated requirement. Add no options, layers or abstractions for needs nobody has stated.
- Handle failures explicitly. Validate input where it enters. Never put secrets in code, logs or messages.
- Test the behaviour the business cares about. A change without a test for its behaviour is not finished.
- Update the documentation that your change makes wrong, in the same change.
- Verify with evidence: run the checks and read their output. A check that did not run is reported as not run, never as passed.

### Phases and approvals

Work follows four phases: research, design, plan, implementation. A person approves the design and the plan before implementation starts. If you cannot tell whether an approval exists, ask.

### Standards

Before you design or change code, run `orqlet standards for --path <path> --phase <phase> --role <role>`. It prints the rules that apply. MUST rules are not optional.

### Generated files

Files listed in `.orqlet/generated.lock.yaml` are generated by Orqlet. Do not edit them by hand. Change their source and run `orqlet upgrade`.
