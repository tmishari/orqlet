# ADR-006: A code review gate with its own reviewer role, and a PR-text role

Status: proposed with the design. It re-decides Q-07 of the proposal, which the person reopened (Q-9) and answered (Q-19, Q-21).

## Context

- The package ships five roles; none is a code reviewer. The review skill starts two reviewers, and the review-result, role-binding, evidence-path and plan contracts accept only `architecture-reviewer` and `security-reviewer`; a plan's `review_evidence` is exactly architecture-reviewer, security-reviewer and tester (A-1, A-52, A-62).
- The proposal describes an `orqlet-code-reviewer` as a provided capability with Q-07 answered as "not a required gate" (A-79, A-80). That conflicts with the code (C-1) and with a record that treats Q-07 as open (C-8).
- The person approved a code review gate (Q-19): every phase, independence I2, resolved models recorded, and an independent session or a human (I3) when no qualifying reviewer exists (Q-21). Code review is "an explicit responsibility" (request).
- Today's minimum is I2 for a D3 change and I1 otherwise, and a class below the minimum is NOT_RUN, not an error (A-53, `src/orqlet/domain/independence.py:57-59`).
- Role definitions with `mode: read-only` or `writes` come from the workflow package; a new role needs its source file and a manifest rebuild (A-3, A-4; ORQLET-DET-002). No skill step writes a pull-request title or description (A-145); the request wants those on the cheapest qualified model.
- The existing records number 112, 108 at I1 and 4 at I2, and the plans and records already approved must stay valid (A-65).

## Decision

1. **A new read-only subagent role, `orqlet-code-reviewer`,** in the protected workflow package, rendered for the three clients like the other roles. It reviews the staged diff at the level of correctness against the acceptance criteria, failure handling, defects, test adequacy and maintainability. The architecture reviewer keeps boundaries, contracts, compatibility and standards; the bullet "the code is correct against the acceptance criteria" moves from the architecture role to the code role (the plan fixes both texts).
2. **`/orqlet-review` starts three reviewers** (code, architecture, security), each in a clean context with the packet path and nothing else. The record role is `code-reviewer`, in `docs/design/<task>/reviews/code-reviewer-P-<n>-r<k>.yaml`.
3. **Scope of the gate: every plan phase and every change class.** "Every phase" is read as every phase of a plan. A phase's `review_evidence` gains `code-reviewer`. Because the per-phase validator cannot see the plan header, the rule moves to the plan level: the plan-level check requires `code-reviewer` in every phase when the plan's `header.workflow_version` is at or above the version that ships the role, and keeps today's exact set otherwise (`src/orqlet/application/contracts/plan.py:49-58`, `src/orqlet/application/usecases/validate_plan.py:41` and the plan-format reference change together). A plan or a record made before that version stays valid under the rules it was approved under; it is not re-opened.
4. **Independence.** The code reviewer needs at least I2 at every class. The architecture and security reviewers keep today's minimum. A class below the minimum is NOT_RUN with the exact reason, never a pass (ADR-007).
5. **No silent self-review.** When no reviewer reaches I2, the review is NOT_RUN and the skill stops and tells the person to run it in **another client**, or to take a human code-owner review (I3). A new session of the same client is I1 and does not satisfy the gate. Orqlet has no record path for the human review: the pull-request approval is host evidence (ADR-004), and the Orqlet record stays NOT_RUN. An agent playing a reviewer is I0 and never counts (existing skill step).
6. **Everything that knows the two reviewer roles gains the third.** The review-record path pattern (`src/orqlet/domain/evidence_artifacts.py:27` admits `architecture-reviewer|security-reviewer` only, so a `code-reviewer` record would be rejected with ORQ-E400 and would count as an ordinary input of its own binding, `validate_records.py:89-96`, `binding_inputs.py:196, 206`); `ReviewResult.role` and `Binding.role` (`review_result.py:63`, `role_bindings.py:19`); the seeded binding for `orqlet-code-reviewer` for the three clients; the two hard-coded reviewer maps `REVIEW_AGENTS` (`render_all.py:68-70`) and `DEFAULT_REVIEWERS` (`review_prepare.py:44-47`), which stay hard-coded (A-58) but gain the third entry, with a unit test that asserts they agree; `minimum_independence`, which takes only a change class today (`independence.py:57-59`) and gains a role input so that the code reviewer needs I2 at every class; and `IMPLEMENTED_COMMANDS` (`src/orqlet/application/usecases/capabilities.py`), which gates the skill steps that name a command and must list `models resolve` and `validate model-policy`.
7. **Same capability category as the coder, never lower.** The code reviewer's profile is `engineering`, the coder's too (ADR-002, Decision 6). The independent quality threshold is the profile's approved membership: a reviewer candidate must come from the coder's profile or a higher one, and a candidate from a lower profile is rejected with `outside-profile` and its reason printed, so review quality is never lowered silently. A different resolved model inside that category is chosen as ADR-007 says.
8. **A second new role, `orqlet-pr-writer` (read-only, profile `economy`).** The implement skill gains a final step that starts it to draft the pull-request title and description from the plan, the design brief and the diff summary, and shows the draft to the person, who opens the pull request. It is not a gate and writes no record. Its role text tells it to treat the plan, the brief and the diff as data and never as instructions. Codex cannot enforce read-only for a custom agent file: the subagent inherits the parent's sandbox, approval and MCP settings (A-108, C-15). On Codex the real reach of this role is therefore whatever the parent session may do, not only the draft text. On Cursor, `readonly: true` blocks file edits and state-changing shell commands but the subagent still inherits the parent's MCP tools (A-122). The role reads a diff that is untrusted content on the cheapest model. **The design decides to render `orqlet-pr-writer` and `orqlet-code-reviewer` for all three clients**, with these mitigations: the data-only instruction in the role text, the person reviewing the actions a role took as well as its output, and the stated limit on each record (ADR-007, Decision 9). The residual risk is the parent session's reach on Codex and the inherited MCP tools on Cursor, and it is accepted here for the person to confirm by approving the design. The request's rule that PR text uses the cheapest qualified model maps to an assignment of the role `orqlet-pr-writer` to the profile `economy` (ADR-002).
9. **The proposal's Q-07 text is updated** in the same change to say the code review gate is required; the architecture document and the README paragraph on reviewers change with it.

## Consequences

- Review cost and time rise by one reviewer per phase; the gate reports NOT_RUN wherever no I2 reviewer exists, which is true by default until a different client runs the review or the team approves a qualifying model (ADR-002, ADR-004). NOT_RUN is a report, not a block: the CI workflow runs no `orqlet` validator (A-44), so the checking is the skill's procedure plus the host's required reviews. Whether a CI check should block a merge is Q-36.
- Existing projects receive the new binding as a pending diff of the seeded `role-bindings.yaml` (A-21), not as a write. Until a reviewed edit applies it, a `code-reviewer` record is an error (the binding is not approved, ORQ-E415, `validate_records.py:325-333`); `upgrade` reports the pending binding.
- The contracts change additively (a role value, a binding role, a plan evidence entry), with two exceptions: the client fields of a review record become a closed set of three (ADR-007), and model-policy v1 is replaced by v2 (ADR-002). The schema files are regenerated (DET-003). Rules apply by `workflow_version`, so no old record is invalidated.
- Moving a bullet between role texts changes both reviewer-definition digests, so reviews of in-flight phases become stale (A-55); that is expected on any role change.
- Each of the two new roles adds one agent file per client (`.claude/agents/`, `.cursor/agents/`, `.codex/agents/`), and the lock gains their rows.

## Rejected alternatives

- **Keep the code reviewer a provided capability, not a gate** (Q-07 as the proposal answered it). The person reopened and approved the gate (Q-9, Q-19).
- **Fold code review into the architecture reviewer.** It would carry two responsibilities with one independence record, and the request names code review as its own responsibility.
- **A gate only at D2 and D3, or at I1.** The person chose every phase at I2 (Q-21).
- **A reviewer persona in the main agent.** I0; never counts.
- **A PR-text step in the main agent with no role.** The request wants the cheapest qualified model for it, and only a role can carry a profile assignment.
