# ADR-007: Reviewer independence, recorded model identity and a fresh context

Status: proposed with the design.

## Context

- `derive_independence` returns I0 for an unapproved binding, I2 when the agent's client differs from the coder's or both known families differ, otherwise I1; it never returns I3 and has no input about context freshness (A-49). A family comes from `model_families` of `role-bindings.yaml`, which is empty here, so every family is unknown (A-46, A-50, I-2). The existing matcher is `fnmatchcase`, which is case-sensitive and does not trim (`src/orqlet/domain/independence.py:17, 34`).
- Review records carry `model_requested` and `model_observed` for the agent and the coder; all 112 recorded reviews hold null in both; nothing produces `model_observed` or the coder's binding (A-51, A-65, U-3, U-4).
- A Cursor session replaced a configured `inherit` with another model and said so only in the session (A-66). Under Cursor Auto the routed model is hidden unless an admin sets Displayed; this team's Router shows it, as display text (A-132, A-156, Q-30). Claude Code reports `modelUsage` and `/tasks`; no fetched Codex page documents a report of a subagent's model (A-99, A-121, U-3).
- The reviewer is told to receive only the packet; one record states that its packet held earlier review notes (A-63, A-64). `review prepare` exports every tracked file into the packet (C-13), and its `diff.patch` is the unfiltered diff from the merge base to the staged tree (`src/orqlet/application/usecases/review_prepare.py:133`; the port `diff_patch(base, head)` takes no path filter, `src/orqlet/application/ports/vcs.py:113`). Whether the 108 I1 reviewers ran in a fresh context is unknown (U-12). Codex's custom agent file cannot enforce read-only and its subagent cleanliness is undocumented (A-108, C-15, U-10).
- A reviewer-definition or code change makes a record stale (ORQ-W410, NOT_RUN) (A-55, A-56). Record validation reads `.orqlet/role-bindings.yaml` from the staged git tree, not from the working tree (`src/orqlet/application/usecases/validate_records.py:306-308`).
- The request says a different resolved identity counts, and effort, speed, context size or an alias that resolves to the same model does not. Q-21 defines I2 as a different client or a known different family and asks that resolved models be recorded.

## Decision

1. **Family comes from the policy as it stood before the change.** When `.orqlet/model-policy.yaml` exists, the family of a recorded model is the `family` of the catalog model that the matching rule of ADR-005 maps it to. Only entries whose `approval.state` is not `proposed` **at the base tree** take part, so neither seed text that no team approved nor an entry added by the change under review can create a difference for that change; when the policy differs between the base and the staged tree, `validate review` adds the closed finding `policy-changed-in-this-change`. Exclusions are the union of both trees (ADR-005). `model_families` of `role-bindings.yaml` (read from the base tree) still applies to a model string that the policy cannot match, and to every string when the policy file was never present, so a project that populated it keeps its I2 on upgrade; where the policy matches a string, the policy's family wins. **The tree matrix:** both trees valid is the normal case; the staged policy unloadable, or deleted (ADR-005), while the base has one, is an error for every record that names a model and never falls back; the base absent or unloadable while the staged policy is valid (the first introduction of the policy, or a repair) is judged on the staged tree for exclusions, with no policy family (so no difference can be established from it) and the finding `policy-changed-in-this-change`, which avoids both a deadlock and a hole. The binding's approval is read from the base tree as well: a binding that exists only in the staged tree is a warning `binding-added-in-this-change`, not an error, so the change that introduces the role is not deadlocked.
2. **Identity is recorded, with its provenance, and only an observed identity counts.** `agent` and `coder_binding` carry `model_requested`, `model_observed` and `identity_source`: `client-reported` means copied from an output channel of the client (usage output, a task card, `/tasks`, `modelUsage`), `person-observed` means seen by the person in the client's interface, and `unknown` means neither; the agent that writes the record is the coder-side agent, so all three are attested. `agent` also carries `selection_source` (ADR-001, Decision 6), and `agent.client` and `coder_binding.client` become the closed set of the three clients (`review_result.py:34, 40` accept any non-empty string today; the plan checks the existing records against the closed set). A requested model that differs from the observed one is a warning that names the catalog ids, or `unmatched`: a substitution is never hidden, and no recorded string is echoed (ADR-002). **A family difference needs both identities observed.** A requested-only model, or `identity_source: unknown`, is an unknown identity and can never establish a difference, because a client may have replaced the pin (A-66, A-96, A-102).
3. **Matching and normalisation** follow the one rule of ADR-005: an alias maps to the model it resolves to, bracketed options and a provider prefix are dropped, and the same logical model is the same identity whatever its effort, speed, context window or alias. Equal known identities never count as a difference; a string that matches nothing is unknown.
4. **Fresh-context attestation.** `agent.context` records `fresh` and `input: packet-only`. It is required for `code-reviewer` records; a missing or false value gives I0 for that role. For the other two roles it is optional so existing records stay valid, and a `false` value gives I0.
5. **The derivation stays a pure function of recorded values** (ORQLET-ARCH-002): approved binding, freshness, clients, observed families. It yields I0, I1 or I2, as Q-21 defines I2: **a different client, or a different known family.** Two readings are the design's own and are listed for the person in section 8 of the brief: "known" family means an *observed* identity (Decision 2), where today's code accepts a requested model (`validate_records.py:319-320`), and a different client on an equal observed model is I2 with a warning, although R-7 says a different resolved model. Two closed warnings keep the weak cases visible and are printed on the gate line of the report: `identity-unknown` (an I2 that rests on a different client while an identity is unknown, so it means *a claimed different client*) and `same-model-different-client` (both observed identities are equal; the request's rule that the same model is not diversity applies within a client, where equal observed identities never count as a family difference). Recording the truth is therefore never worse than omitting it. A free-text sentence in `capability_limits` is no longer the mechanism.
6. **I3 is not derived from a record.** It is a human code-owner review on the host, by someone other than the author (ADR-004), and Orqlet has no record path for it. A review that cannot reach I2 stays NOT_RUN with its reasons in `capability_limits`; the pull-request approval is the fallback.
7. **Excluded models are invalid evidence** (ADR-005): a record naming one gives an error and I0.
8. **The packet carries no earlier conclusion.** `review prepare` leaves `docs/design/**/reviews/**`, and every path that the design manifest names as a review note (`DesignReview.note` is any repository path, `design_set.py:126-128`), out of the snapshot, the context copies and `diff.patch` (the VCS port's `diff_patch` gains a path-exclusion parameter). Excluded paths appear in neither the `omitted` list nor `MANIFEST.json`, which would reveal that earlier rounds exist. The design-manifest copy lists note paths and holds no conclusion. A test scans the whole packet for a sentinel string taken from an earlier record, and it runs against the real git adapter, not only a fake. Whether `git diff-tree` honours an exclude pathspec (`vcs_git.py:167`) is an unknown the plan must establish; the fallback is to filter the patch by its file headers after it is produced. Every round rebuilds the whole packet from the staged snapshot and diff, so a re-review covers the full agreed scope.
9. **Read-only is stated, not assumed.** Claude Code uses a tool allow-list. Cursor `readonly: true` blocks file edits and state-changing shell commands, but the subagent still inherits the parent's MCP tools (A-122). For Codex a record's `capability_limits` holds the fixed phrase "read-only is not enforced by this client"; `validate review` warns when a `codex` record omits it. A tree changed during a review shows when the record's components are recomputed (ORQ-W410).
10. **Two entry points, one parser.** The policy is read from the working tree for `upgrade`, `validate model-policy` and `models resolve`, and from the base and the staged git trees for `validate review` (Decision 1), so that independence is derived from the exact snapshot that was reviewed and not from the change's own edit of the policy.
11. **The review skill gains the diversity step.** Before it starts the code reviewer it records the coder's model (requested and observed, with the source), runs `orqlet models resolve --role code-reviewer --client <client> --different-family-from <catalog id of the coder's model> [--coder-profile <profile>]` (the flag takes a catalog id that the matching rule found; when the coder's model is `unmatched` the skill omits the flag and the review reports that no family difference could be shown; `--coder-profile` defaults to `engineering` for the code reviewer), and starts the reviewer on the first qualifying candidate when the client lets a spawn name a model. It records requested and observed for the reviewer. If none qualifies, it reports NOT_RUN and asks for another client or a human review.

## Consequences

- The derived class is a statement about recorded, attested values, as the module docstring already says; no tool verifies a model string, a freshness flag or an observed identity.
- Because only observed identities count, the family route to I2 needs a client that reports the model: Cursor with the Router displayed, or Claude Code's `/tasks`. In Codex, I2 comes only from running the review in a different client.
- Under Cursor Auto with the Router displaying the model, both identities can be observed; the person or the agent copies display text, which the matching rule handles.
- Existing records are unaffected: the new fields are optional for the older roles, every existing model field is null, and the observed-only rule changes no existing result.
- Within one client, only Cursor documents naming a third-party model for a subagent (I-1); Claude Code's per-invocation model takes Claude aliases only (A-101) and Codex inherits the provider (A-108).
- R-10 raises the minimum for the code reviewer to I2 at every class, where D1 and D2 changes needed I1. For D3 changes today's derivation already read the two client strings; for D1 and D2 those strings now decide the outcome. They are free text today and become a closed set of three (Decision 2), but they stay attested by the agent whose work is reviewed, so in the dominant case I2 rests on a claimed different client, and the report says so on the gate line.
- Evidence of an I3 or of the host's checks is outside Orqlet: until Q-36 is answered, no command in CI turns a NOT_RUN review into a blocked merge.

## Rejected alternatives

- **Derive I3 from record fields.** No field can show a human; the existing docstring says so (`src/orqlet/domain/independence.py:9-10`).
- **Require an observed model on every record.** Codex gives none (U-3); the gate would be NOT_RUN for Codex permanently.
- **Let a requested model stand in for an observed one.** A replaced pin would then give a false I2.
- **Keep `model_families` in `role-bindings.yaml` as the only source.** It is empty (I-2) and would duplicate the catalog's `family`.
- **Treat `inherit` as a known identity.** It names nothing; under Auto it can differ between turns (I-10).
- **Reject any review that ran on the coder's own model, whatever the client** (a narrowing of Q-21). It would reject a different client on an unknown model that Q-21 accepts, and it would reward leaving the identity out. The weak cases are warned about instead.
- **Read the policy only from the staged tree.** The change under review could remove an exclusion or add a favourable family and pass against its own edit.
