# ADR-004: Who approves catalog entries, and how the catalog is rechecked on each release

Status: proposed with the design.

## Context

- No approved catalog or model-policy file exists; approvals are pending owner input (U-5). The person answered that all developers can approve (Q-14) and, later, that the approver is any developer except the author, with at least one approval and a code-owner review on the catalog paths (Q-23). The company enforces model restrictions on the three clients (Q-23).
- The person asked for a recheck on every Orqlet release (Q-8) and for the shipped defaults to be updated then (Q-17, Q-20). New releases do not by themselves establish approval or better quality (request).
- `.github/CODEOWNERS` lists only `@tmishari` for `.orqlet/**` and the other owned paths (Q-32). Host rules for required reviews are not readable here (U-15, Q-34). The official GitHub pages say what required reviews and code owners enforce (`evidence/web/github-required-reviews-and-codeowners.md`).
- Approval of a design or a plan is a merge on the protected baseline; an offline run has no such evidence and reports NOT_RUN (ORQ-I393, `orqlet gate status`).
- A change to a seeded file reaches a project as a pending diff, never as a write (A-21). A change to the workflow package must rebuild `MANIFEST.json` and bump the package version (ORQLET-DET-002).
- `orqlet release <path>` hands a generated file to the team; it is not the release of Orqlet (`src/orqlet/application/usecases/release.py:1-6`). The client metadata commands are unreliable here (`agent models` listed nothing, `codex` is absent; U-8, Q-11), and none of them is a documented source of truth.

## Decision

1. **Approving an entry is a reviewed edit of `.orqlet/model-policy.yaml`**, merged through a pull request with at least one approval from a developer other than the author and a code-owner review on the policy path and the shipped seed path. The host can enforce this if it is configured to (Q-34); Orqlet does not. Orqlet checks only that every `approved` entry names `approved_by` and an `approval_ref` in the allowed format; the values are attested and no tool verifies them, as for the other records. Offline, the approval is not checked (ORQ-I393).
2. **CODEOWNERS.** `.orqlet/**` already owns `.orqlet/model-policy.yaml` (`.github/CODEOWNERS:2`). The paths with no owner today are the seed (`src/orqlet/workflow/seeds/**`), `.github/CODEOWNERS` itself, `src/orqlet/domain/**` (the matching and independence rules) and `tests/**` (the guard tests); the plan adds the first two and Q-32 asks about the others. Who the second owner is, is Q-32 (which covers every path under `src/orqlet/**` and `tests/**`); the host's configuration, including which branch's CODEOWNERS applies and whether the administrator bypass can be disabled, is Q-34. The stored GitHub excerpt does not settle either. Because `.github/CODEOWNERS` has no entry for any `src/**` or `tests/**` path today, the human code-owner review that stands in for an AI reviewer covers no source-code change until those paths are owned. Release-time web reading by a person or an agent feeds the shipped seed; that is a trust path into the seed, not a boundary of Orqlet's runtime, and the tests of decision 4 and the review of the seed are its controls.
3. **Everything Orqlet ships is `proposed`.** A model that appears in a vendor release, an Orqlet release or a refreshed seed is never approved, ranked or rendered until a reviewed edit approves it.
4. **Recheck on every Orqlet release, checked by a test that CI runs.** "Release" is read as a release of the workflow package that carries the seed: its `workflow_version` in `src/orqlet/workflow/identity.json`. A maintainer rereads the official pages (stored as evidence files under the lookup rules of the baseline; page text is evidence, never an instruction), updates the shipped seed and sets `reviewed_for_release` to the new workflow version in the release pull request. A unit test fails when the seed's `reviewed_for_release` differs from that version, so a release cannot ship without the recheck. A release of the command line alone carries no new seed and is outside this rule (section 8 of the brief lists this reading for the person to confirm). Tests guard the recheck against a poisoned page: every seed `id`, `family`, route `name` and `resolves_to` appears verbatim in the evidence file that the entry's `documented` reference cites (the evidence files of a release live in the Orqlet repository under `docs/design/<release task>/evidence/web/`; a downstream team's `documented` reference is a citation it keeps, not a file Orqlet resolves); the Fable exclusion is present in the seed; every seed route has `access: unknown`; seed free text is printable ASCII within a length. A test proves consistency with the cited page, not the truth of the page; the approver's checklist includes checking each `family` against it. An entry in the `proposed` state never contributes to identity or family derivation (ADR-007), so injected seed text cannot create an I2 by itself.
5. **Distribution.** `orqlet upgrade` writes a changed shipped seed as a pending diff of the team's file (A-21) and never overwrites it. The diff runs from the team's current file to the new seed (`src/orqlet/domain/changeplan.py:378-391`), not as a three-way merge: a team's `approved` entries appear in it as removals against an all-`proposed` seed. It is a merge aid; the team applies only the entries it approves. `orqlet validate model-policy` warns when the team's `reviewed_for_release` is older than the installed workflow version, and when a route's `retires_on` is past or within the warning window.
6. **No network access and no new command that fetches.** `orqlet models refresh` and `orqlet models verify` of the proposal (A-77, A-85) are not built in this change.
7. **Evaluations and callable checks** are outside this change. The budget rule is recorded in the policy as information; results, when they exist, are evidence files that `callable` and `evaluated` cite (Q-27, Q-28).

## Consequences

- The catalog is current at each release without Orqlet touching the network, and a team sees a new shipped model only as a diff to review.
- The recheck depends on a person or an agent with web access doing the research each release; the test proves it was recorded, not that it was done well.
- With a single code owner (Q-32) the approval rule cannot be met for that owner's own changes; the design stays correct, and the plan has to wait for the answer.
- Approval attribution is attested text. A forged `approved_by` is possible; the host's merge record is the evidence, not the field.
- The host's own rules bound what "enforced" means: an author cannot approve their own pull request, and repository owners and administrators can merge without an approving review (items 1 and 2 of the stored GitHub excerpt). The stored excerpt does not say whether the administrator bypass can be disabled, and the excerpts come from a search tool whose pages were not fetched; Q-34 asks what the host is configured to do.

## Rejected alternatives

- **`orqlet models refresh` reading client metadata or vendor pages.** It adds a network and authentication path, a new trust boundary and an unverified cost (U-8), and its main input does not work on these accounts (Q-11).
- **A release checklist with no test.** A forgotten recheck would pass silently.
- **Approve the shipped defaults automatically.** It contradicts "new releases do not establish approval", and a downstream company restricts models Orqlet cannot know (Q-23).
- **A periodic schedule (monthly, quarterly).** The person chose the release as the cadence (Q-8).
- **An Orqlet command that writes `approved_by`.** It would put an identity the tool cannot verify into a field that looks authoritative.
