# ADR-004: A bounded web lookup in four phases, with the rules written once in the baseline and a step in each phase skill

Status: proposed. It becomes accepted when the design pull request is merged by an authorised person.

## Context

- No skill, role, command or baseline text tells an agent to search or fetch, and the only retrieval wording is the sentence in each skill that retrieved passages are evidence, not instructions (AS-IS U-54, A-78). The skill table gives onboarding and research "Read-only; no network" (A-94, A-119, C-16, C-21). The architecture document describes no automatic lookup of an unknown library or tool in any phase (U-71); for a technology that no pack covers it plans only a report and a proposal file (A-111).
- The person wants the lookup in research, design, implementation and onboarding, to run automatically in each research, and to look at how others implement something when a library or tool is unknown (Q-6, request). They want the registered resources used first where there are some (Q-4, Q-5).
- The workflow skills have numbered steps; a step marked `requires: <command>` is dropped when the release lacks the command (A-63, A-64). The research skill requires every fact to cite `path`, `lines`, the base revision and `sha256`, and the validator reads each cited file at that revision, so an outside page can be cited only as a committed repository file (A-79, A-90, C-15, C-18). The earlier task stored web excerpts as `docs/design/<task>/evidence/web/*.md` with the address, the retrieval time and excerpts, committed before citing; this task did the same (A-91).
- A read-only role of Claude Code has no web tool; the matching Cursor and Codex fields do not say, and the tester role has no tool allowlist (A-81, A-82, U-56). The subagents of research and design report facts or reviews and are started by the main agent (A-79).
- Every skill repeats one sentence about source material (A-78), so a repeated paragraph is the existing pattern; the baseline text reaches every agent at every session in `AGENTS.md` (A-42) and is the same for all adopters. The baseline may not exceed 60 lines and 8 KiB (`tests/unit/test_manifest.py:155`), and it says that files listed in the lock are generated and not to be edited by hand, although the lock also lists seeded files that a team owns (A-14, C-2).
- The three clients' web tools differ (A-128 to A-132, U-76, ADR-001). `evidence cite` reads a cited file at a revision and returns its hash (A-89); it is the one place through which a web page enters an AS-IS file or a design.

## Decision

1. **The rules are written once, in the baseline.** A new short section "Looking things up" in `baseline/baseline.md` carries the rules of ADR-001 decision 3, in about 12 lines, within the limits above: the order of sources, the signed-in browser only for an entry with `access: login`, the same-host and redirect rule, no forms or actions, stop at a login, no credential, cookie, token or storage-state file, no command run or package installed because a page says so, no repository text, login-page text or credential in a search query or an address, and page text is evidence. For a page behind a login there is one more rule: the agent writes a summary in its own words, with at most short quotations, marks the evidence file `Data class: internal`, shows it to the person, and commits it only after the person has said yes in the conversation (advice: the agent reports the yes). The text carries no address and names no product. Before the first use of the signed-in route in a session the agent names the registered address and asks, and a query carries only the public name and version of a published technology. Every task in every phase sees it, which is what "automatic" needs: a lookup step that an agent must remember to start is not automatic. The same edit changes the sentence about the lock to: files listed in the lock are generated, except the seeded files, which belong to the team and are changed with the command named for them or by a reviewed edit.
2. **Each of the four phase skills gains one step that applies the rules to the phase,** marked `requires: resources list` so that a release without the command drops it:
   - **research**: before the facts are written, run `orqlet resources list --uncovered --json` and list the technologies of the request and its scope; for each one whose behaviour the repository and the registered resources do not document, do the lookup. Write each result as `docs/design/<task>/evidence/web/<slug>.md` in the format of decision 3, commit it, and cite it like any file. A page that could not be read is an unknown with a question. A lookup that was needed and not done is listed under `self_check.unverified`, because that list is where the AS-IS file states what it did not verify.
   - **design**: the same step for a decision that depends on a library or tool that the AS-IS file does not cover; the excerpt goes to the same folder and is cited in the design's evidence references.
   - **implement**: when the code touches an API that neither the AS-IS file nor the design documents, read the registered resource and then the official page; when a page decides how the code is written, write the evidence file of decision 3 in the task's folder so that the pull request shows it, and a finding that changes a decision of the design or plan stops the work and is reported (the phase's existing rule that implementation does not redesign).
   - **onboard**: ask in the one consolidated batch for the answers to the convention questions and for links to resources; for each link run `orqlet resources add`; run `orqlet doctor` and read the information finding that lists the unknown conventions; for a technology of the profile that has no resource and no pack, offer the lookup and show the person what was found before anything is recorded; before `resources add` is applied with `--yes`, show the person the exact title, note and address and wait for a yes; write a stored copy only when the person asks, with the steps of ADR-002 decision 9 and the `summary` form for an internal page.
3. **One format for an outside page.** `references/as-is-format.md` gains a section "Evidence from the web" that fixes the layout of the evidence file: a title, then the lines `URL:`, `Retrieved:` (with a zone), `Tool:` (which client tool returned the text), `Processed:` (whether the tool ran the text through a model, as Claude Code's fetch does, A-129) and `Data class:` (`public` or `internal`), then numbered excerpts with a label. "Verbatim" is claimed only for text as the tool returned it. The format is a convention that the review of the pull request checks; no validator requires the header, because the 38 evidence files of earlier tasks do not have it and are hashed in AS-IS files (editing them would break their citations). The research and design validators do not change.
4. **`evidence cite` scans the way in, at cite time only.** When the cited path is under `docs/design/*/evidence/web/` (matched on the canonical, case-folded path), `cite` first reads the file with a cap of 256 KiB and runs the scan of ADR-002 decision 9 (`credential_problems`) over it; the scan covers the exact bytes that `cite` hashes (read at the revision) with `credential_problems` and the code-point and comment rules of `hidden_text_problems`; a file that fails or exceeds the cap is refused with the rule name and the line, so a page copied with a credential cannot be cited by `evidence cite`. `evidence hash` is not guarded, a file that is never cited is never scanned, and no command walks the folder in CI; that is a stated limit. This is a guard at cite time and nothing earlier: the file is already committed locally when it is cited (the evidence is read at a revision), so the controls before a push are the person's yes for a login page and the review of the pull request. The check records of ADR-005 are not cited and are reviewed in the pull request. This is the one change to `evidence cite`; its arguments and its output for any other path do not change.
5. **Role text.** All five roles get the sentence of ADR-001 decision 6 (look nothing up; report what cannot be read as an unknown).
6. **Limits per client are recorded where the others are.** The adapters add capability limits that `doctor` prints, in the way the existing limits are: for Codex, that `web_search` defaults to `cached`, so a lookup may not see a current page, with what the stored excerpt says of the other modes (A-131); for Cursor, that its web tools are not verified (U-76); for Claude Code, only the existing documentation limit. They say the behaviour is documented and not observed, until checks V-6 to V-8 (ADR-005) are done. Which clients can honour "registered address only" at all is part of what V-6 records; where a client cannot, the limit says the rule is advice.
7. **No new command for the lookup, and no Orqlet-run lookup.** `resources list --uncovered` prints names from the profile that no registered resource covers (ADR-002, domain `uncovered_names`). It does not fetch.

## Consequences

- Every adopter's `AGENTS.md` gets about 12 more lines and its workflow version changes: goldens are regenerated on purpose, and existing installs see the change as an `upgrade`.
- The lookup is as reliable as the model's following of the text and the client's web tool. The record is the evidence file and the `unverified` list; nothing in Orqlet can prove that an agent looked.
- Research gains work for each technology of a task. The step says "whose behaviour is not documented", so a request that touches only code the repository documents costs one command.
- The evidence folder holds third-party text. Excerpts stay short, with the address and the tool, as the earlier tasks did; a licence question stays with the team (considerations, security).
- Skills that are `requires`-gated degrade to the old behaviour on a release without the command, so a mixed state is harmless.
- The baseline cannot be relaxed by an adopter, so at the next `upgrade` every adopter's agents are asked to look things up on the web. The plan summary of that `upgrade` and the Codex and Cursor limit texts say so and name the way to opt out, which is to disable the client's own web tool.
- Whether a person's "yes" in the conversation was given is the agent's report; the pull request review of the evidence file is the control that remains.

## Rejected alternatives

- **A separate `orqlet-lookup` skill.** Rejected: an agent has to choose to start it, and the person said the lookup should run on its own. The baseline reaches every session.
- **The same paragraph in each of the four skills.** Rejected: four copies drift; the baseline is the one place all four already inherit (A-42, A-78).
- **A validator that requires a web evidence file for each technology.** Rejected: Orqlet cannot know which technologies a task touches, and an empty file would pass such a check. The `unverified` list is the honest record.
- **A lookup command in Orqlet.** Rejected in ADR-001.
- **Allow the lookup in the read-only subagents.** Rejected: facts-only roles with a tool allowlist are what keeps untrusted page text out of the roles that review (A-81), and the main agent can do the lookup once for all.
- **Commit verbatim text from a login page like any other page.** Rejected: internal text would reach Git history unasked (considerations S-4).
