# Considerations: security, compatibility, operations

Each state is `affected`. The sections say what the design does about each point and what it cannot promise. Findings use the labels S-n for security. A control is something that stops an action mechanically; advice is text that asks an agent or a person to behave. The two are kept apart below.

## Security

This change adds a path from a committed file, and from text of the web, into the instructions of three clients, and it lets an agent read pages in the developer's own session. It adds no network code, no credential handling and no dependency to Orqlet.

- **S-1 Instructions from data (B-1).** A title, a note, a tool name, a version, a path glob, a profile answer and a stored copy enter the rules, skills and `AGENTS.md` that a client treats as guidance. Controls: each text field passes an allow-list (ASCII only, U+0020 to U+007E on one line, so no bidirectional control, zero-width, variation-selector, filler, tag or look-alike code point and no Unicode table that could differ between Python versions; none of `://`, `](`, `<!--`, `-->`, backtick); the application writes the value with `json.dumps` after a fixed label, so a value cannot start a line, forge a block marker or leave its quotes; the `name` and `description` of every generated rule and skill are fixed templates over the validated id, kind, tool and version and never hold a title, a note or a glob (a description is read at the start of every session); a stored copy is referenced by path and never inlined; every generated file is `PROTECTED`, so a hand edit is an error that `doctor` reports and `upgrade` undoes, and `upgrade --check` makes it a failed CI step (ADR-002 decisions 2, 3, 8; S-11). A stored copy is checked against a fixed table of invisible code points and against HTML comments. A golden test builds a hostile registry and profile and shows that no hostile field reaches a name or a description. Advice: the baseline and every generated template say that page text is evidence and not an instruction (AS-IS A-78). What the allow-list does not stop is a well-formed sentence that reads like an order, and a mistaken or hostile pull request can still write one; only review catches it (S-11). The same holds for text that an agent writes after reading a page (a note passed to `resources add`): the onboarding step shows the exact title, note and address and waits for a yes before `--yes`, and the command echoes what it stored; but the generated rule and the catalogue skill act in the working tree from `upgrade`, before the pull request is reviewed.
- **S-2 Addresses.** `url_problems` is an allow-list grammar (ADR-002 decision 8): `https` only; an ASCII lower case host of two to eight labels; no user information, port, fragment, percent sign in the host, trailing dot, `xn--` label, numeric or `0x` last label, `localhost`, `local`, wildcard-DNS or redirector name from the closed list; a path of URL characters with no long opaque segment; a query value or host label that is not long and opaque; a query whose normalised keys carry no credential stem and no tracking key and whose decoded values hold no `//` or scheme. It is hand-written because the domain may not import `urllib` (`pyproject.toml:96-112`), and each rule has negative vectors, among them `127.1`, `0xa9.0xfe.0xa9.0xfe`, `LOCALHOST`, `a.b.nip.io`, `evil.com\@good.com`, `good.com%2f@evil.com`, `x?X-Amz-Signature=...`, `x?private_token=...` and a long hex path segment. The lists are examples and not exhaustive, an intranet host (including a metadata name such as `metadata.google.internal`) is legitimate for a `login` entry, and so the review of the host in the pull request is the only control there. Orqlet fetches nothing; the agent's own fetch tool has its own refusals (A-130) and prompts.
- **S-3 Session reuse (B-3).** A client that reads through the developer's browser session can reach every page and action that the developer can (A-160, A-161). Advice only: the baseline also says that the first use of the signed-in route in a session is announced to the developer and confirmed even when no login page appears (a browser that is already signed in shows none), that the host of a login page is told to the developer, and that a search query or an address carries only the public name and version of a published technology and no login-page text or credential, which is the step that sends text out once a page, the developer's session and a web tool meet; a registry entry with `access: login` is a switch that turns the signed-in route on for its host, so a change of that field or of an address is a privilege change that review must treat as one. The baseline restricts the agent to registered addresses, official documentation and same-host links, to the browser route only for an `access: login` entry, no forms or actions, a stop at a login page and at a redirect to another host, and no command run or package installed because a page says so. Controls: none has been observed. The client's permission prompts are not shown by any stored excerpt (V-6, V-7), and the design relies on none. The one mechanical option that the evidence names is a client-side domain list such as Codex's `allowed_domains`, which does not restrict connectors or MCP servers (A-132); this change generates no client settings. Orqlet adds no mechanical control for the lookup and does not claim one. A persistent browser profile keeps the login on disk (A-161); where it lives is the developer's and the client's, and no file of this change names, generates or asks for it. Playwright's `--storage-state` file is a credential: the baseline forbids the agent to create or read one, the README tells adopters to keep such files and profile folders out of Git and to use a browser profile that is signed in only to the team's sites, and Orqlet has no guard for them because it cannot know the names that each tool uses.
- **S-4 Internal content in the repository.** A page behind a login is internal by definition (`access: login`). Its stored copy puts internal text in Git history, which may be wider than the page's audience (a public or forked repository, a cloud agent, a contractor), and history cannot be cleaned afterwards; Orqlet cannot see offline whether the repository is public. Controls: only the form `summary` is allowed for such an entry; the copy is scanned; `validate resources`, run in CI, walks `docs/resources/` and fails for any entry that is not a regular `<id>.md` named by an entry and for a `login` copy that is not a summary (both labels, `access` and `form`, are declared by the maintainer), so a copy that was written without `attach` cannot merge unnoticed. `attach` also asks at a terminal, also with `--yes`, and without a terminal stops with needs-input; that prompt is advice-grade, because it tests only that the standard streams are terminals (`tty_prompter.py:18-19`) and an agent that is given or allocates a pseudo-terminal can answer it. For research and design the evidence file of a login page is a summary in the agent's own words, marked `Data class: internal`, shown to the person and committed only after a yes in the conversation (advice, since the agent reports the yes; the pull request review of the file remains), and `evidence cite` refuses to cite a file under `evidence/web/` that fails the scan or exceeds the size cap. That guard runs at cite time, after the local commit and before any push; nothing earlier than the person's yes and the review of the pull request keeps internal text out of a local commit. Licence and permission of a copy of a public page stay with the team; the registry carries the address, the form and the time, so a reviewer can see what was copied from where.
- **S-5 Secrets in the registry, a copy or an evidence file.** `credential_problems` is a bounded scan that reports the rule name and the line and never the text (ORQLET-SEC-003). Its rules: token prefixes of well-known providers, the JWT shape, private-key block markers, user information in an address, an `Authorization` value with a token-like body, and `key=value` pairs whose key is a credential word with a token-like value. Its patterns are linear-time, a line above 4096 characters is itself a finding, and a timed test with hostile input is part of phase 1. It is written for Markdown, not copied from the configuration scan of the integrations task (which has no private-key rule and flags long lines and `Authorization: Bearer` placeholders); the plan may reuse its patterns if that task has merged by then. A false positive is cleared by editing the copy; there is no bypass flag. A scan cannot find every secret; it is a guard, and review is the control.
- **S-6 Orqlet's own surface.** No network import is added; domain and application stay free of `socket`, `http`, `urllib` and `subprocess` (A-83, A-84). Git is reached only through the allow-listed runner with fixed configuration and a scrubbed environment (`git_runner.py:18-31,50`); the new method uses `rev-list` and `cat-file`, which are already on the list, with full ids resolved first. Files are read through the `FileSystem` port, which refuses links and traversal, and the strict YAML loader, which refuses anchors, aliases, merge keys, duplicate keys and odd tags and bounds size, depth and nodes (ORQLET-SEC-002); the stored copy path is derived from a validated id, which cannot be a Windows device name or hold a path separator. Digests are SHA-256 (ORQLET-SEC-003). Every write goes through `apply_plan` with journal and backup (ORQLET-SAFE-001); the new write paths get fault tests (ORQLET-TEST-002).
- **S-7 Resource exhaustion.** The shared glob matcher recurses over every split point of each `**` segment, so its cost grows with the path length to the power of the number of `**` segments (`src/orqlet/domain/globs.py:8-21`). The design does not claim otherwise: a branch pattern may hold at most one `**` and at most 8 segments, a branch name above 255 characters or 32 segments is a finding before matching, and a timed test with hostile input is part of phase 1. The commit grammar is a fixed scan; the check reads at most 200 subjects of at most 1 KiB each with a fixed number of Git processes; the registry, the copies and the strings have the caps of `component.md`.
- **S-8 Output of the check (B-4).** A branch name and commit subjects are typed by a contributor. One function (`printable`) escapes every echo of them and of any other text from the repository: only U+0020 to U+007E pass, every other character, DEL and the C0 controls included, is shown as an escape, cut at 100 characters, after a fixed code prefix, so no output line starts with contributor text and a CI log command (`::error::`) cannot be formed. The text is never passed to a shell, a template or an `eval`. The README warns not to pipe the output into a job summary unescaped. An agent that a maintainer asks to fix a failed check reads at most 100 escaped characters of a subject; that is a bound on size and not a control, because 100 ASCII characters can still be an instruction.
- **S-9 Egress by the clients (B-2).** Orqlet cannot see what a client sends to its vendor. The architecture document says Claude Code's fetch sends the host name to the vendor unless a setting opts out (Section 13.3; not verified here). More important, the text of every page the client reads goes to the client's model vendor, and for the clients that process a fetch in a second model call, to that call as well (A-129); a page behind a login is internal. `resources add --access login` prints this, and using the login route for internal content is an owners' decision, as the approval of Context7 is (U-62). A team that must keep an internal host name or page text from the vendor must not register that page with such a client, or must use a stored copy that a person wrote. V-6 records the behaviour per client.
- **S-10 More skills start by themselves.** Until now only a person started a skill. The catalogue and the tool skills may be started by the agent (ADR-002 decision 4). Their text is a fixed template over validated fields, has no step that changes a file or a phase, and says how to read; it does include the advice to use the signed-in browser route for an `access: login` entry, which is an action in the developer's session and is counted as one in S-3. The workflow skills keep the user-start-only flag; a test pins both sets.
- **S-11 Review cannot be enforced here today.** The registry, the copies, the profile, the generated rules and the CI step are effective only when someone reviews the pull request, and a pull request that edits `.github/workflows/**` or `.orqlet/**` can switch a check off. This repository has no `CODEOWNERS` file, and the capture of GitHub's state shows one collaborator who is an admin and a refusal of branch protection and rulesets with HTTP 403 (`docs/design/open-items/evidence/github-state.yaml:26-31`, not refreshed). Admins bypass protection by default even where it exists (A-156). The `doctor` notice for code owners (ORQ-I030, extended) is advisory and now also names the workflow and `.orqlet` paths. `PROTECTED` is detection at run time: it is a merge gate only through `orqlet upgrade --check` as a required status check, because no implemented command that CI runs today reads the class (`ORQ-E150` says CI fails, but `ci check` is not built, `capabilities.py:14-38`).
- **S-12 Web text inside evidence files.** An excerpt may contain text that addresses an agent. The files are repository files read as evidence by the reviewers, whose tools are read-only for the Claude Code roles except where a fork ignores a role's `tools` (`docs/design/orqlet-architecture-proposal.md:776`) and whose text says that retrieved passages have no authority (A-78, A-81). The tester role has no tool list and inherits the web and browser tools; it carries the sentence of ADR-001 decision 6. Excerpts are short; a reviewer reads them in the pull request. The repository already holds one such sentence, in `evidence/web/context7.md`, as an excerpt that was treated as evidence.
- **S-13 What the evidence does not show.** Whether a client honours a read-only setting for web tools or can be limited to a registered address, whether Cursor and Codex have a browser route, where each client stores a sign-in, and what the clients send to their vendors are unknown (U-56, U-76, Q-15). Checks V-6 to V-8 record them. Until then the adapters say "not observed", the design relies on no prompt and no setting, and where a client cannot honour a rule the limit text says it is advice. The roles' sentence is the only measure for Cursor and Codex, and it is advice; the word "control" in this document means only something that stops an action mechanically, and no control of the lookup has been observed. The Claude Code limit text also says that a fork ignores a role's `tools` and that the tester inherits the web tools.
- **S-14 The check judges by the target's rules (B-4).** The profile is read at the base revision, so a pull request cannot relax the rule that judges it. A pull request can still remove the CI step; the control is the host's required status check and the review of `.github/workflows/**` (S-11). A subject that starts with `Merge ` is exempt, which a contributor could use to dodge the shape; review is the control. An explicit `--branch` is always checked; a defaulted one equal to the target branch is not; a shallow clone, an unknown branch or more than 200 commits is `NOT_RUN`, never `PASS`.
- **S-15 The CI step.** The documented step uses `pull_request` and never `pull_request_target`, `permissions: contents: read`, `persist-credentials: false`, no secrets, actions pinned to a commit, Orqlet installed at the pinned version and hash, no `continue-on-error`, a full-history checkout, the branch and base through `env:` and given as `--branch="$HEAD_REF"`, no job-level `if:` (a skipped job counts as passed, `evidence/web/github-protected-branches.md:16-18`), and the README pins it with a test; it also has a `timeout-minutes`, and Orqlet is installed from the repository at the version that `cli.pinned` names, written into the workflow file and not read from the pull request's own versions file (no CLI hash is recorded and there is no published package). Its steps are `validate resources`, `conventions check` and `upgrade --check`. A branch name is attacker-chosen text and is never interpolated into a script.
- **S-16 Fixtures and records.** Fixtures use placeholders only. A negative test builds a credential-shaped string from parts so that no real-looking token is committed (ORQLET-SEC-003). Check records of ADR-005 are reviewed in the pull request; no command scans them, because they are not cited.
- **S-17 Limits that stay with the team.** Licence and permission of a copy; whether the repository is public; freshness, which is advisory because a hand edit of `retrieved_at` or `ttl_days` can make a copy look fresh and because the hash and the time are bookkeeping, not provenance (one pull request can change a file and its record); personal names or e-mail addresses that a team writes into `reviewers` and that reach `AGENTS.md`; and whether an agent that was told to ask the person for a yes did so. The README lists these, and `doctor` says that freshness is advisory.
- **S-18 Evidence files and a second scan.** `evidence cite` scans the exact bytes it hashes with `credential_problems` and `hidden_text_problems`. `evidence hash` is not guarded, a file that is never cited is never scanned and no command walks `evidence/web/` in CI, so the guard is at cite time and the stated limit is that an uncited file is unscanned.
- **S-19 Security-relevant paths.** The manifest lists `security_globs` for the files that parse untrusted input or render into instruction channels, and declares them in a `security` expected change, so the class stays D3 even if a boundary were later removed.

## Compatibility

- **Profile contract.** `orqlet.project-profile/v1` gains optional fields with defaults. Section 20.2 calls an additive change to a versioned schema minor, so the contract stays `v1` and no waiver is needed. Every existing profile loads in the new release. The contract is closed (`extra="forbid"`), so an older Orqlet refuses a profile that holds the new fields; the pin in `.orqlet/versions.yaml` controls that. The committed JSON Schema of the profile is regenerated.
- **Existing installs and `doctor`.** The new unknown conventions are reported by one information finding and not by ORQ-W181, so the exit code of `doctor` for an existing install does not change when it upgrades; the three existing repository questions keep their findings. `init` asks the new questions of a new install; an existing install answers them with `orqlet profile answer` when it chooses to.
- **New contract and file.** `orqlet.resources/v1` and `.orqlet/resources.yaml` are new. `init` writes an empty registry and `upgrade` writes it when absent; the file is seeded, `compose` receives its current bytes, and a hand edit or a merge of two branches is up to date (ADR-002 decision 5). A registry that fails its contract stops `init` (re-run), `upgrade` and `explain` before any plan, so a typo cannot delete generated files.
- **Composition.** `compose` takes the parsed registry and its bytes next to the profile and stops discarding the profile; `data_files` seeds the registry; `build_render_request` gains two parameters. `init`, `upgrade` and `explain` change together, and so do their tests.
- **Classification.** One branch of `classify` is added: a seeded file whose current text equals the new text and differs from the record is up to date, and the record advances. The case where all three are equal keeps its result, and the existing test rows do not change. It also quiets the repeated empty proposal for a hand-edited profile (U-18).
- **Generated output.** For an adopter with no resource and no convention answer the only new generated bytes are the baseline section. With answers or a registry there are the `conventions` block and the resource files, all `PROTECTED`. Goldens that carry the workflow version change once, on purpose, with `--update-golden` and never in CI (ORQLET-DET-001). New goldens cover a registry with a rule, a tool skill and a catalogue for each client, and a hostile registry. The skill file of a workflow skill is byte-identical except for the version marker.
- **Names.** New generated names (`orqlet-resource-<id>`, `orqlet-tool-<id>`, `orqlet-resources`) use the reserved prefix and fit the managed folders (A-41); a hand-made file with the same name was already an error of `doctor`.
- **Commands.** `IMPLEMENTED_COMMANDS` gains `resources add`, `resources update`, `resources remove`, `resources attach`, `resources list`, `validate resources` and `conventions check`, each in the phase that builds it; no existing command changes its options or exit codes. `init` asks about links only when it has a terminal; without one it prints the hint to run `orqlet resources add`, because a link needs an id, a title, a kind and a note that one option cannot carry.
- **Workflow package.** The baseline, four skills, five roles and one reference file change, one schema is added and one regenerated; each phase that touches the package rebuilds the manifest, and the identity and the release record follow once (ORQLET-DET-002, ORQLET-DET-003). The baseline stays within 60 lines and 8 KiB. This task's own design and plan headers go stale on `workflow_version` and `protected_set_digest` when `orqlet upgrade` is run in this repository, which is the last phase (ORQ-W390).
- **Evidence files of earlier tasks.** `evidence cite` scans a file under `evidence/web/` and requires no header, so the 38 existing evidence files, which are hashed in AS-IS files, stay valid; a new file follows the format of `references/as-is-format.md` by convention and review.
- **Documents made wrong.** The architecture document's rows "Read-only; no network" (Section 17.10), Section 15.8, Sections 17.2, 22, 23 and 24.2, and the README's status and command list change in the same change (A-76, A-94, A-95, A-119, C-4).
- **Interplay with the integrations task.** That design's `.orqlet/integrations.yaml` and MCP files are separate. The MCP route of ADR-001 depends on its later phases, and check V-9 waits for them. If its first phase merges, its credential patterns can be reused (S-5); nothing here depends on it.

## Operations

- **Commands and exit codes.** `resources` commands return 0 on success, 3 when input is refused, 4 when `--yes` or a terminal is needed, as `profile answer` does (A-73). `validate resources` and `conventions check` return 0 on `PASS` and 5 on `FAIL` or `NOT_RUN`, as the other checks do (C-13).
- **CI.** A repository adds three steps to its own workflow after it has answered its conventions: `orqlet validate resources`, `orqlet conventions check --branch="$HEAD_REF" --base="origin/$BASE_REF"` and `orqlet upgrade --check` (which exits 1 when a generated file is behind its sources or a protected one was edited), written as in S-15, with a clone deep enough to hold the base. The README gets the snippet and a test pins it. Making the step a required status check is a host setting that a person with admin rights makes. This repository's workflow is not changed by this design (ADR-003 decision 8).
- **Refreshing generated files.** After any edit, `orqlet upgrade --check` reports that changes are available and `orqlet upgrade` applies them as a journalled change that `orqlet rollback` can undo. The registry, the profile and the copies are ordinary tracked files, so a revert also works.
- **Freshness.** `doctor` compares `retrieved_at` plus `ttl_days` with the clock and warns once per copy; nothing is deleted or refetched, because Orqlet fetches nothing. The person refreshes a copy by reading the page again and running `attach`.
- **Size.** Codex reads at most 32 KiB of the `AGENTS.md` chain (A-140). The baseline section adds about 12 lines and the block is at most 12 lines and 3 KiB. The catalogue skill grows with the registry, up to the cap of 100 entries; the other clients list skills by name and description. V-3 and V-5 measure it.
- **Support.** A client with no web tool, or a web tool that is off, cached or unverified, cannot do a lookup. `doctor` prints the documented limit for each enabled client, and the agent's answer is an unknown with a question, which the person sees in the AS-IS file.
- **Rollout.** Existing installs get the new files, the baseline section and the block at the next `upgrade`. A team that does nothing keeps an empty registry and no block; no behaviour of an existing command changes.
