# ADR-005: Build order, release steps, what is not built, and the checks with test sessions

Status: proposed. It becomes accepted when the design pull request is merged by an authorised person.

## Context

- Skills, rules, blocks and workflow text are generated for three clients whose behaviour is documented and not observed: no client was opened, the Cursor `globs` format, the duplicate skill listing, the Codex reading of `disable-model-invocation`, path-scoped skills in Claude Code and Codex, the size limits and what any agent does with a skill are all unknown (AS-IS U-22, U-23, U-27 to U-29, U-36). The person allowed checks with test sessions in each client (Q-14).
- The skill renderer, the capability limits and the client adapters have golden tests, and any change to the workflow package rebuilds its `MANIFEST.json` and bumps the package version before a release (ORQLET-DET-001, ORQLET-DET-002, ORQLET-DET-003). CI runs `tools/build_manifest.py --check`, and the committed JSON Schemas under `src/orqlet/workflow/schemas` are files of the package (`.github/workflows/ci.yml:62-64`, `src/orqlet/application/usecases/workflow_manifest.py:15-26`). A command that a skill step names must be in `IMPLEMENTED_COMMANDS`, and a test keeps that set equal to the commands of the application (A-63, A-64).
- Anything that writes files needs a fault test that stops it after each step (ORQLET-TEST-002), and only two such tests exist today, for `init` and `upgrade`; the write paths of `profile answer`, `profile approve`, `release` and `rollback` are not shown to have one (U-49, Q-14).
- The earlier design of the integrations task ordered its phases so that validators come before renderers, so that a renderer is never built before the check of its output, and made one change at a time that a person could verify with a test account (mcp-or-plugins ADR-003, ADR-004).
- Documents the change makes wrong: the architecture document's rows "Read-only; no network" for onboarding and research (Section 17.10), Section 15.8 on documentation access, the table of commands and of what may use the network (Sections 22 and 23), Section 17.2 and the profile example (Section 24.2) for the new fields, and the README's status and commands (A-76, A-94, A-95, A-119, C-4, C-21).
- Only `build_render_request` sees both the resources and the `MUST` rules of the packs, so only it can find two sources that would claim the same generated file name; `ValidateServices` has no standards packs (`src/orqlet/application/usecases/validation.py:30-35`, `render_request.py:73-80`).

## Decision

1. **Phase order for the plan** (the plan decides the exact split and may merge or split these, but not reorder a phase before one that it needs):
   1. The pure modules `domain/resources.py` and `domain/conventions.py` with their negative, property and hostile-input tests (including the timed test of the branch matcher and the URL vectors of ADR-002), and the one-branch change of `classify` with its test. Nothing else depends on them yet.
   2. The contracts (`orqlet.resources/v1`, the additive profile fields), their JSON Schemas through `tools/export_schemas.py`, the rebuilt `MANIFEST.json`, valid and invalid fixtures, and `resources_path`, `parse_resources` and `load_resources`.
   3. The registry reaches composition: `compose` and `data_files` take `resources` and `resources_bytes` and seed `.orqlet/resources.yaml`; `init`, `upgrade` and `explain` load it, refuse on an invalid registry before any plan, and tests show that no file is deleted; the pure builders `resources_with` and `resources_without`; `validate resources`; the `doctor` findings and the extended code-owners notice. No client file is rendered yet.
   4. The edit commands `resources add|update|remove|attach|list`, the link prompt of `init`, their fault tests (ORQLET-TEST-002: each write path stopped after each step, and a re-run of the `init` prompt converges), and the `--access login` notice.
   5. The convention questions: the new answer keys and vocabulary, `_acceptable`, `_repository`, `_with_pr_template`, the information finding, and the `draft_profile` defaults for an old profile; a test that an answer given at `init` survives.
   6. Rendering: `ConventionsView`, `RenderRequest.conventions`, `ClientSkill.agent_may_start`, `resources_view`, the renderers and the three adapters, the name check in the skill renderer, the capability limits, the name-collision check in `build_render_request`, `compose` building the request from the profile and the registry, and the goldens regenerated on purpose, with a golden test of a hostile registry.
   7. `conventions check`: `Vcs.commit_subjects` with a real-Git test, the Git adapter and the fake, the use case, the command, and the README snippet with its test.
   8. The workflow package: the baseline section and the changed sentence about the lock, the four skill steps, the five role sentences, the reference file, the `evidence cite` guard, the version bump and the release record; then the documents and the README, and, last, the person runs `orqlet upgrade` in this repository.
   Every phase that changes a file of `src/orqlet/workflow/**` (a schema, a skill, the baseline) rebuilds `MANIFEST.json` in that same phase, because CI checks it on every pull request; the version bump and the release record are made once, in phase 8. A command is added to `IMPLEMENTED_COMMANDS` in the phase that builds it. The `resources` parameter that phase 3 adds to `compose` is unused until phase 6 and is acknowledged with `del`, as the profile was (the lint rule for unused arguments). The goldens regenerate in phase 6 and again in phase 8, when the baseline and the version change. A phase never builds a generator before the validator of its output, and the workflow text of phase 8 comes after the commands that its steps name exist. Phase 8 keeps the baseline within 60 lines and 8 KiB.
2. **The checks with test sessions.** Each is done by a person with a test account or a test project, on the client version in use, and recorded as a file under `docs/design/team-conventions-resources/evidence/checks/`. A claim of the generated files that depends on a check is not made in a skill, a limit or the README before it is done; until then the adapters keep the limit "not observed". A phase may merge before its check: the check gates the claim, not the code. That includes phase 8, which ships the baseline section and the skill steps as advice with the limits "not observed"; what stays out of the text until its check is done is any statement that a client honours `access: login` routing or stops before using the signed-in route, that a skill starts by itself, or that an agent reads a stored copy first.

3. **Release steps follow the workflow package edits:** rebuild `MANIFEST.json`, bump `identity.json`, add the release record, regenerate the goldens and the committed schemas on purpose, and propose the `versions.yaml` change. This task's own design and plan headers go stale on `workflow_version` and `protected_set_digest` when the person runs `orqlet upgrade`, which is why that step is last (ORQ-W390).
4. **Not built in this change, by decision:** an Orqlet fetcher and `orqlet standards import`; local Git hooks; any call to the code host; a check of a pull request's title, description, size, merge strategy, reviewers or required checks; a `level` or a `MUST` rule made from a link; a read of stored copies by the knowledge analysis; packaging as a plugin; Context7 or another documentation server; a nested `AGENTS.md` per path for Codex; a guard against tracked browser storage-state files (Orqlet cannot know the names that each tool uses, so the baseline forbids creating them and the README tells adopters to keep them out of Git); the Java, .NET, Ruby and PHP scanners that the plans list. Each is a separate decision with its own design.
5. **Finding codes** for the new findings (resources, stored copies, conventions, the information finding, the extended notice) are allocated by the plan from the next free numbers of each family and listed in a table of finding codes that the plan adds to the README (it has only a table of commands today); the design fixes the behaviour, not the numbers.
6. **For the person to confirm by merging the design:** the narrowing of "checked" (Q-11) to two of eight conventions, with the other six recorded and told; the deferral of the fetcher and the unnamed Context7 (Q-12), and that the login route for internal content is an owners' decision; the reading of "Yes" (Q-13) as all three routes (the developer's browser, the user's own MCP sign-in, a stored copy); fault tests only for the write paths that this change adds (Q-14); ASCII-only text fields in this release; the one-branch change of `classify`; and the `branch_patterns` fact next to the prose `branch_naming` (prose is for agents, patterns are for the tool).
7. **Carried as unknown, to be answered by a check or a later task:** how Cursor honours `paths` on a skill and whether Claude Code and Codex do (U-22); whether `doctor` should report a hand-edited seeded file as drift (U-9); the effect of the rule that Codex stops at 32 KiB (U-36), including where the managed blocks sit in a long `AGENTS.md` (V-3 measures it; a `doctor` size warning is not built here); whether the knowledge analysis should read stored copies.

## Consequences

- The plan has eight phases at most, each with a test that stands alone, and the first four ship nothing a client reads, so the risk is borne where it is cheapest.
- Eleven checks need a person and test accounts; some need a second client or a test SAML site that the person has to provide. A check that is not done leaves its claim out, which is the stated cost.
- The fault tests of the four edit commands and of the `init` link prompt are new work, and they close part of U-49 for what this change adds, not for the old commands.
- The workflow version changes for every adopter: a bump with regenerated goldens, once.

## Rejected alternatives

- **Build the skills text first, then the commands.** Rejected: a skill step names a command, and a step that names a missing one is dropped by design; the text would ship empty.
- **One large change.** Rejected: nothing in it would be verifiable alone, and the goldens of three clients would change together with the contract.
- **Observe client behaviour in unit tests.** Not possible: the suite has no network and starts no agent (ORQLET-NOMODEL-001, ORQLET-TEST-001).
- **Skip the checks and state the limits.** Rejected for the claims that the person asked for, because a skill that "all devs will have" must in fact load; V-1 to V-5 and V-10 are the smallest set that shows it.
- **Rebuild the manifest once, in the last phase.** Rejected: CI checks it on every pull request, and phase 2 adds a schema.
