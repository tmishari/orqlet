# ADR-003: Team conventions live in the profile, reach agents in one block of `AGENTS.md`, and a CI check covers the part that a tool can check

Status: proposed. It becomes accepted when the design pull request is merged by an authorised person.

## Context

- `init` asks three repository questions (`target_branch`, `branch_naming`, `commit_convention`); the answers are stored as facts in the profile, and the last two say "leave empty if not" (AS-IS A-5, A-6, A-74). `reviewers` and `merge_strategy` are plain strings that default to `unknown`, are not answer keys and are asked by nothing (A-7, A-75, U-1, U-12, U-14, C-7). Nothing asks about a branch model, gitflow, a release or hotfix flow, a pull-request shape or required checks (U-1, U-47, U-65, U-66, C-19). An empty answer cannot say "there is no rule" apart from "not answered" (C-6).
- The profile never reaches a generated file: `compose` executes `del profile`, no adapter reads these values, and the baseline text does not contain the word `branch` (A-12, U-3, U-11). The target branch is used only to find the merge base of a review (A-20).
- The architecture document puts these facts in the profile (Section 17.2, A-99, A-100) and plans a `commit-msg` hook that "enforces the profile's commit convention" and a CI check; neither is built, and the two documents disagree about whether the first release was to build them (A-101, C-23). Nothing in the documents defines a pull-request shape or a branch model (U-65).
- An empty answer is dropped, a change of any fact withdraws the profile's approval, and `doctor` reads the unknown facts back as ORQ-W180 and ORQ-W181, a warning that makes its exit code non-zero (A-14, A-15; `src/orqlet/application/usecases/diagnose.py:313-335`, `src/orqlet/interface/cli/commands/lifecycle.py:52-56`). `FactValue` allows no value without evidence or a maintainer's answer, and no unknown without a question (`src/orqlet/application/contracts/common.py:62-76`). `_with_pr_template` rebuilds `PullRequests` from `template`, `reviewers` and `merge_strategy` only, and `_repository` updates three top-level facts (`init_project.py:326-334`, `init_questions.py:229-241`).
- `gate status` is offline (A-87). The Git runner allows `rev-parse`, `for-each-ref`, `rev-list`, `merge-base`, `ls-files`, `ls-tree`, `cat-file`, `diff-tree`, `diff-index`, `write-tree` and `check-ignore` only (A-86). The `Vcs` port has `current_branch()` and `recent_commits()` that no use case calls (U-5, U-13), and `read_at(revision, path)`. The shared glob matcher recurses over every split point of each `**` segment, so its cost grows as the path length to the power of the number of `**` segments (`src/orqlet/domain/globs.py:8-21`).
- The person wants the five topics asked and recorded: the branch model and gitflow, branch naming and commit convention, the shape of a pull request, merge strategy and required checks, release and hotfix flow (Q-3); and wants them checked (Q-11). The person left the place of the check to industry practice (Q-16). The evidence found: Pro Git says client-side hooks are not copied when a repository is cloned, that `git commit --no-verify` bypasses `pre-commit`, and that a policy is better enforced on the server side (A-151 to A-153); the commitlint guide lints a pull request's commits on CI (A-154); GitHub branch protection can require reviews, status checks, code owner approval, linear history and signed commits, and by default does not bind admins (A-155 to A-157); DORA advises protecting branches so that pull requests merge only when tests pass and warns against an overly heavy review process (A-158, A-159). The evidence does not say how a tool checks a branch name or the shape of a pull request description (Q-16).
- The AGENTS.md page says commit and pull-request guidelines belong in it, and that the nearest nested file wins (A-163). Claude Code reads `AGENTS.md` through the bridge, Cursor and Codex read it natively, and Codex stops at 32 KiB for the whole chain (A-42, A-138 to A-140). The baseline may not exceed 60 lines and 8 KiB (`tests/unit/test_manifest.py:155`).
- Section 20.2 says additive changes to a versioned schema are minor and breaking changes are major.

## Decision

1. **The answers are profile facts, added in place.** `orqlet.project-profile/v1` gains optional fields, so an existing profile still loads and an older Orqlet refuses a new one (the contract is closed; the pin in `.orqlet/versions.yaml` controls it). This is an additive, minor change under Section 20.2, so the contract stays `v1` and no waiver is needed. `Repository` gains `branch_model`, `release_flow` and `branch_patterns`; `PullRequests` gains `shape` and `required_checks`. All five are `FactValue`, each with a default that is an unknown with its question, so that "unknown" and "none" stay different and a list needs no second representation: a list is stored as one comma-separated text and split where it is used. `merge_strategy` and `reviewers` keep their type; the text `unknown` is their unanswered state. `_with_pr_template` and `_repository` are changed to keep and to set these fields (`model_copy`, nested keys), and a test shows that an answer given at `init` survives the rest of `init`.
2. **The vocabulary is small and closed where a tool checks it.** The new keys are `repository.branch_model`, `repository.branch_patterns`, `repository.release_flow`, `repository.pull_requests.shape`, `repository.pull_requests.merge_strategy`, `repository.pull_requests.reviewers` and `repository.pull_requests.required_checks`.
   - `branch_model` is `trunk-based`, `github-flow`, `gitflow` or `other: <text>` (A-146 to A-149, A-158); `merge_strategy` is `squash`, `rebase`, `merge-commit` or `other: <text>`; `commit_convention` stays free text and `conventional-commits` is the one value that the check understands.
   - `branch_patterns` and `required_checks` are comma-separated lists of at most 12 items of at most 60 characters whose whole text is at most 160 characters, so the block never has to cut a list; the other answers are cut at 160 characters when they are shown (the profile keeps the full value), inside the existing answer limit of 200 characters. A branch pattern is a glob in the existing dialect (`*` stays inside a segment, `**` spans segments) with at most one `**` and at most 8 segments, so the matcher's cost stays quadratic at worst (`pattern_problems`); a longer branch name than 255 characters or with more than 32 segments is a finding before matching.
   - Every answer that reaches an instruction channel passes `text_problems` (ADR-002 decision 8: ASCII only, one line, no link or markup sequences) when it is given, and again when it is rendered; a value that fails there is left out of the block with a finding. `is_checkable_convention` is true when the answer, lower-cased with spaces and underscores read as hyphens, equals `conventional-commits`.
   - The answer `none` is a recorded value that means "the team has no rule"; it is no longer unknown, and agents are told not to invent one. `init` and `profile answer` ask a question again only while the fact is unknown.
   - The new unknown facts are reported by one information finding, not by ORQ-W181, so the exit code of `doctor` for an existing install does not change when it upgrades; `init` asks them, and `profile answer` sets them later.
3. **Agents get the answers in one managed block.** `compose` stops discarding the profile and calls `conventions_view`, which returns a `ConventionsView` and the findings of the values it left out. The view holds the finished lines: the application checks and quotes each value (ADR-002 decision 8) and the adapter only writes the lines between the markers. The lines are the answered conventions, the names of the unknown ones and the number of registered resources. Each client adapter writes it as a second shared block, `conventions`, in `AGENTS.md` next to the `baseline` block (the merge already keys files by path and block). The block exists only when at least one convention is answered or the registry is not empty. Content: one line per answered convention, one line "Not decided: <names>. Ask the person; do not invent one." and, when the registry is not empty, one line that points to the skill `orqlet-resources`. Each value is written as a JSON string after a fixed label (ADR-002 decision 8), and the block is at most 12 lines and 3 KiB; lines beyond twelve are dropped and a final line says that the rest is in the profile. The block's class is `PROTECTED`, like the baseline block, because its content is a pure function of validated profile values: a hand edit is the error ORQ-E150 and `upgrade` restores it. It is not part of the protected workflow set. The profile's approval state is not rendered; `doctor` already warns about a draft profile (ORQ-W180).
4. **The check covers what a tool can decide offline.** `orqlet conventions check [--branch NAME] [--base REF] [--head REF]` is read-only and offline. It checks (a) the branch name against `branch_patterns`, and (b) the subject of every commit in `base..head` against the Conventional Commits shape (a type of lower case letters, digits and hyphens that starts with a letter; an optional scope in parentheses of letters, digits and `._/-`; an optional `!`; a colon, one space and a description that does not start with a space) when the convention is `conventional-commits`; a subject that starts with `Merge ` is exempt, which a contributor could use to dodge the shape, and review of the pull request is the control for that. Under a squash merge the subject that lands is the pull-request title, which the check never sees; the README says so.
   - **Which rules.** The profile is read at the base revision with `Vcs.read_at`, not from the pull request's own tree, so a pull request cannot relax the profile rule that judges it (it can still remove the CI step or change the workflow file, which review and the host's required check cover); a change of the profile takes effect after it is merged.
   - **Resolution.** Base and head are resolved to full ids first (`Vcs.resolve`, which refuses a name that could be read as an option or a revision expression), and `rev-list` and `cat-file` get ids only. Defaults, for a local run only (CI always passes `--base`): head `HEAD`; branch from `Vcs.current_branch()`; base, when `--base` is not given, the target branch named by the profile of the working tree, resolved remote-qualified and then plain as `review prepare` does. That resolution is a few lines in `conventions_check` itself, because the helper of `review prepare` is private to `binding_inputs.py` and promoting it would add public names outside this change; the rules are then read at the base that was found. An explicit `--branch` is always checked; a defaulted branch that equals the target branch is not checked and the output says so in an explicit line, and the verdict is then `NOT_RUN` for the branch check, not `PASS`.
   - **Verdict.** `FAIL` if any check fails. `NOT_RUN`, with the reason, if nothing is configured, the convention is free text, the base cannot be resolved or its name is refused by `check_ref_name` (a shallow clone, a name such as `release/1.0+x`), the profile at the base is missing, unreadable or of a version this release does not read, there is no merge base, the branch is unknown (detached head without `--branch`), more than 200 commits are in the range, or any Git call fails or exceeds the runner's output or time limits (`VcsError`); never a traceback. The patterns read from the base profile are checked again with `pattern_problems` before use, and one that fails is a `NOT_RUN` reason. `PASS` only if every configured check ran and passed; nothing that did not run is `PASS` (baseline). Exit codes are those of the other checks (5 for `FAIL` and `NOT_RUN`).
   - **Output.** One function (`printable`) escapes every echo of a branch or a subject: only U+0020 to U+007E pass, and every other character, DEL and the C0 controls included, is shown as an escape; text is cut at 100 characters and follows a fixed code prefix, so no line starts with text from a contributor. The same function is used for every echo of text that comes from the repository (the registry, the profile, a stored copy) by `validate resources`, `doctor` and `resources list`. A subject is cut at 1 KiB after reading; `cat-file` returns the whole commit object and the runner's own output and time limits bound it, and exceeding them is a `NOT_RUN` reason; the whole range is read with a fixed number of Git processes.
5. **CI on the code host is the check that decides; a local hook is deferred.** The evidence puts enforcement on the server, because a local hook is not copied by a clone and can be skipped (A-151, A-152). The design therefore builds the command for CI and documents the step for an adopter's workflow. It builds no `commit-msg` hook, no hook installer and no change to `.git/hooks`; a later change may add a hook that calls the same use case as a convenience, not as a gate. The documented step fixes: `on: pull_request` and never `pull_request_target`; `permissions: contents: read`, `persist-credentials: false`, no secrets and a `timeout-minutes`; actions pinned to a commit; Orqlet installed from the repository at the version that `cli.pinned` of `.orqlet/versions.yaml` names, written into the workflow file itself and not read from the pull request's own versions file (no CLI hash is recorded today, `render_all.py:204-214`, and there is no published package, `README.md:50-59`); no `continue-on-error`; a checkout with full history; the branch and the base passed through `env:` and given as `--branch="$HEAD_REF"` and `--base="origin/$BASE_REF"`, never interpolated into the script; and no job-level `if:`, because a skipped job counts as passed for a required status check (`evidence/web/github-protected-branches.md:16-18`). The steps are `orqlet validate resources`, `orqlet conventions check ...` and `orqlet upgrade --check`; the last exits non-zero when a registry or profile change has not been rendered or a protected generated file was edited by hand (`lifecycle.py:113-120`), which is what makes the generated files a merge gate when the step is required. An adopter adds the step after the conventions are answered, because `NOT_RUN` exits 5. The README pins the snippet with a test. Whether the step blocks a merge depends on a person making it a required status check on the host; Orqlet cannot set or read that.
6. **What stays recorded and told, not checked.** The pull-request shape, the merge strategy, the required checks, the reviewers and the release and hotfix flow are told to agents and kept in the profile. A tool could enforce the merge strategy (linear history needs squash or rebase) and the required checks only through the host's branch protection (A-155), which needs the host's API and an admin; the design builds neither. `doctor` prints one information finding when any of these is answered: Orqlet cannot read the host, so confirm the branch protection settings. Of the eight conventions (branch model, branch naming, commit convention, pull-request shape, merge strategy, required checks, reviewers, release and hotfix flow), two are checked by the tool (branch naming through patterns, and the commit convention when it is `conventional-commits`) and six are told and recorded; the person's answer "checked" (Q-11) is met for those two, and that is stated here and in the README so that nobody takes the other six for enforced.
7. **The approval rule is unchanged.** Answering a convention changes the profile and withdraws an approval (ORQ-I070), and `profile approve` stays a person's act (A-14, A-16).
8. **This repository's own CI is not changed here.** A step for `validate resources` and `conventions check` is documented for adopters and left to the person for this repository. The capture of 2026-10-26 (`docs/design/open-items/evidence/github-state.yaml:26-31`, not refreshed here) shows that the host refused branch protection and rulesets for this repository with HTTP 403 ("Upgrade to GitHub Pro or make this repository public"), so a required status check may not be possible here.

## Consequences

- `init` asks up to seven more questions; a maintainer can answer `none` or leave a fact unknown, and `doctor` keeps listing the unknown ones without a change of its exit code for an existing install. A non-interactive `init` still reports the open questions and does not guess.
- Every developer's agent sees the same conventions at the same place. A change of an answer reaches agents after `orqlet upgrade` and a merged pull request; `upgrade --check` shows it as available.
- The check is useful only as a required status check, and Orqlet cannot make it one. Without that, a failed step is advice. Admins bypass branch protection by default (A-156), so the control is as strong as the host's setting.
- The Conventional Commits shape rejects Git's default `Revert "..."` subject; a team that uses it writes `revert:` or leaves the convention as free text. No exemption list is invented beyond `Merge `.
- The `Vcs` port gains one method, `commit_subjects`, which returns at most 201 commits so that the use case can see that the range is longer than the 200 that the check reads, built on `rev-list` and `cat-file`, which the runner already allows, so the allow-list does not change. The plan checks that the runner accepts the options of a batched `cat-file`.
- `required_checks` in the profile is a statement of the team, told to agents. It is a different thing from `required_checks` of the workflow policy contract, which no command writes today (U-8). The block says "the team's required checks" and the documentation names the difference.

## Rejected alternatives

- **A new file `.orqlet/conventions.yaml`.** Rejected: the architecture puts these facts in the profile (A-99), `doctor` reads unknowns from the profile only (A-15), and a second approval path would be needed. The profile's additive fields cost less.
- **Put the conventions into the baseline text.** Rejected: the baseline is the same bytes for every adopter and is part of the protected set (A-42, A-43); a team's branch rule is not the workflow's.
- **Regular expressions for branch names and commit subjects, supplied by the team.** Rejected: a pattern from a committed file, matched against text typed by a contributor, is a denial-of-service risk, and a glob list with one `**` and one fixed grammar are enough for the stated needs. Add nothing nobody asked for.
- **Read the profile from the pull request's own tree.** Rejected: the same pull request could relax the rule that judges it (decision 4).
- **Build the local hooks now.** Rejected for the evidence in decision 5. The architecture's `commit-msg` hook also rejects AI trailers (A-101), which is a separate decision.
- **Check the pull-request title, description, size and merge strategy.** Rejected: the title and description exist only in the host's data, and reading them needs its API and a token, which is network and a credential (ADR-001). A team can put a title rule into the commit convention and the host's squash setting.
- **Ask the five topics at `init` only.** Rejected: the person asked for a way to add, update and remove later (Q-8); `profile answer` gives it without a new command.
- **Report the new unknown facts as ORQ-W181.** Rejected: it would turn a warning exit code on for every existing install at its next upgrade.
