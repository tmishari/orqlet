# ADR-001: Check reuse and re-checking without a cache

## Context

The phase contract asks the coder and the tester to cite every source again before each check (A-14, A-15). Implement runs the full input check and two gate status calls per phase (A-13). Plan and design repeat gate status and hashing (A-11, A-12). Rework rounds redo every record and review (A-18), and the person reported repeated checks around review and testing (Q-9). Sessions show a median of 15 full pytest runs per implement session, and no rerun without an edit in between (A-31, A-32). No result persists between CLI calls (A-25). Evidence cite takes one range per call (A-26). Once an earlier implement phase is committed, gate status reports the plan stale with ORQ-W390, and implement stops until the person confirms the planned-work row; gate status reads no commit trailer (A-83, A-84).

Citations A-n in this ADR name facts of `as-is.md` at 86e07abc (sha256 3fe613104a96638cd6fbae1b862092f3df563ab1fcfd71ca438b8c78ae4bfd3f), the file this design was written against. The current file, bound at 16afd3c (sha256 3526c5beefbd6ab4f4d0e36be6a4f16bdb9214664f822c8987ee765f9e32f77a), holds A-85 to A-126 and describes the code after this task, so it does not restate the older facts. A-83 and A-84 are restated there as A-106, A-111 and A-112; A-26, one range per `evidence cite` call, is now A-118.

## Decision

1. Each distinct source of a phase's checks is cited once per phase, by whichever role runs a check first. The tester's report lists the citations it made (path, lines, revision and sha256) and the `orqlet evidence hash` of each cited file, so the coder can reuse them; the record schema does not change. Before relying on a reused citation, the coder compares its sha256 with the plan's recorded hash and checks its path and revision against the "Values from artifacts" character rule. Before every later run, `orqlet evidence hash` on the cited files, each one single-quoted argument, must print the recorded hashes, which shows that neither a commit nor a working-tree edit changed them, and the cited files are still tracked; only a changed file is cited again, with the person's yes as today.
2. A check result is reused while no file has been edited since its last passing run, the command is the same and the plan's environment values are the same. At each passing run the agent records HEAD (`git rev-parse HEAD`) and the `orqlet evidence hash` of the cited files and of the phase's file-operation paths, and all must be unchanged before a reuse. That comparison is necessary, not sufficient: a file outside those paths can change unnoticed, so the rule still requires that no edit was made. Every rerun names its reason: a changed input, a gate, or a rework round.
3. During iteration the coder runs a targeted form of a check when the plan names one; the full form runs once before review and once per rework round, after all of that round's fixes.
4. Implement runs `gate status --phase` once per phase. From the second phase on, the commits of earlier phases change the plan's operation paths, which are its scope, and paths under the design's and the AS-IS file's `scope.paths`, so gate status reports ORQ-W390 and NOT_RUN by construction (A-83). The agent matches that cause to the planned-work row of the stale-input matrix and the person confirms it, as today, once per phase. A later phase reuses the validators' result when that confirmed planned work is the only stale cause and the input check's "Current" step shows no change to an approved file. Gate status does not recognise planned work itself, because it reads no trailer and the trailer and the author are claims, not proof (A-84).
5. Plan runs gate status once and uses that output for its header. Design hashes its files once before starting the reviewers and records those hashes, `manifest.yaml` included, in each note. Before it stops, the design skill compares the recorded hashes with the files and with the manifest, and a difference starts a new round. `validate design` checks only that the notes exist, so this comparison is the check.
6. Design and code reviews stop after three rounds with one consolidated report; with a blocking finding still open, the person decides between a rework, a design revision and a human review. A nested review reuses implement's model suggestion and standards output.
7. `orqlet evidence cite` accepts several `FILE LINES` pairs in one call. `--revision` applies to every pair. The use case returns one result per pair: `data.citations` lists them in today's entry shape, a single pair also keeps today's top-level fields, and any failing pair makes the verdict FAIL while the others are still returned. A refused or failing pair carries no revision and no sha256. Each pair under `evidence/web/` gets today's credential and hidden-character scan. The human text prints one snippet line per pair, its subject lists the files, and it has no action line, which belongs to the validators and `gate status` only.

## Consequences

- Fewer CLI calls and citations per phase, and fewer full suite runs, with the same gates and reviewers.
- Reuse depends on the agent following text rules; the file hashes, the HEAD comparison and the validators' hash checks make most stale reuse visible, but nothing in code enforces "no edit since the last run".
- `orqlet evidence hash` reads files through the FileSystem port and starts no program. Git commands the agent runs in the person's shell, such as the input check's `git diff`, run outside the hardened Git runner, and a working-tree comparison can start a clean filter that the repository's configuration names. This design adds no such command; the input check's existing ones remain. While main's lint, types and tests jobs are red (Q-14), CI cannot separate new failures from known ones, so the full local run before review is the gate that counts.
- Later implement phases still meet ORQ-W390 and one confirmation of the planned-work row per phase; this ADR removes the repeated validator runs, not that confirmation. A new file that no check cites, such as a test configuration file, is caught by the full run before review, not by the hash comparison.
- `data.citations` is additive; a reader of today's single-pair output sees no change.
- The rules move into the phase contract once, so skills shrink.
- A plan without a targeted check form keeps today's behaviour.

## Rejected alternatives

- A persistent result cache in the CLI keyed by input hashes: a new persisted format, invalidation code for every check kind and a new place for stale results, for a problem that text rules and file hashes already cover.
- Orqlet runs the project's checks itself: Orqlet would start project commands, a new trust boundary and a change to its role of preparing and validating.
- Keep re-citation before every check: no evidence shows the cited sources change between checks of one phase (A-32), and the hash comparison detects the case where they do.
- `git status --porcelain` and a working-tree `git diff` for the comparison: they run outside the hardened Git runner and can start programs that the repository's configuration names, and porcelain output misses a second edit to a file already modified.
- Rely on the tester's reported hashes without comparing them with the plan: a changed source could then run unreviewed.
- No round cap for design reviews: one task needed 15 rounds per role (A-58); the code review already stops at three (A-20).
