# ADR-007: The security controls carried over from 0.5.2

## Context

Orqlet reads files that a repository controls, starts Git and writes into the project and the data directory (ORQLET-SEC-001, ORQLET-SEC-002, ORQLET-SAFE-001). In 0.5.2 these controls live in a few modules whose exact rules are the normative source; the hostile-configuration test that found some of them was removed with the test suite (`src/orqlet/adapters/git/git_runner.py` lines 34-36). A port that lists fewer rules would weaken a control without anyone noticing. Line numbers below are at the base revision 3e3c311. Rules marked "new" differ from 0.5.2 on purpose and are listed as expected differences in the parity fixture (ADR-002).

## Decision

1. **Processes.** Only the Git module starts processes. The process module is a private child of the Git module in `orqlet-adapters` (`git::process`), invisible to the rest of the crate; no ProcessRunner port is exposed, since in 0.5.2 the only callers are the Git modules (`src/orqlet/interface/cli/wiring.py` lines 108, 170 and 207; A-16). A child gets an empty environment (`env_clear`) plus the allow-list of `src/orqlet/adapters/process/environment.py` lines 7-32, names compared case-insensitively. A timeout or the output cap kills the child.
2. **Git.** GitRunner carries the full rule set of `src/orqlet/adapters/git/git_runner.py` lines 18-116: the base arguments `-c core.fsmonitor=false -c core.hooksPath=`; the eleven allowed subcommands; the forbidden options per subcommand, and any `ls-files` short-option cluster holding `m`; `diff-index` only with `--cached`; `--no-ext-diff --no-textconv` added to `diff-tree` and `diff-index`; options read only before `--`; `init` reachable only through the branch-name check (no `refs/` or `-` prefix, not `@`, then `check-ref-format --branch`); the extra variables `LC_ALL=C`, `GIT_TERMINAL_PROMPT=0`, `GIT_PAGER=cat`, `GIT_OPTIONAL_LOCKS=0`; 30 s and 16 MiB by default (A-17, A-18). New: a long option that is a prefix of a forbidden option is refused as well, since Git may accept an unambiguous prefix (not looked up; the rule only refuses more). Every value that comes from a repository file is checked before any process starts: a revision is `HEAD` or a full 40- or 64-digit object id (`src/orqlet/adapters/git/objects.py` lines 11-17); a path read through `cat-file --batch` holds no line feed or NUL (lines 26-28); a ref name matches the pattern and refusals of `src/orqlet/application/ports/vcs.py` lines 28-38; exclusions are non-empty, NUL-free and canonical paths (lines 41-56); pathspecs are passed only after `--`.
3. **Strict YAML** (`src/orqlet/adapters/fs/yaml_loader.py` lines 1-7, 27-70 and 87-131; A-13). Every YAML document is read into Orqlet's own generic tree, built from the parser's events with the original scalar text and style, and only then converted into a contract type by serde, without type coercion. The tree enforces: input at most 1 MiB; UTF-8 only; only YAML-printable characters; one document; no aliases or anchors; no merge keys; no duplicate keys; string keys only; only the core tags str, int, float, bool, null, seq and map; depth 32 and 50,000 nodes. Plain scalars resolve as in lines 36-49 and are constructed as 0.5.2's safe constructor does: booleans `true`, `True`, `TRUE`, `false`, `False`, `FALSE`; integers matching `[-+]?[0-9]+`; floats without an `inf` or `nan` form; null as `~`, `null`, `Null`, `NULL` or empty; everything else, dates and `0x` forms included, stays a string. New: a plain integer outside the signed and unsigned 64-bit ranges, or a float outside the f64 range, is refused as decision 4 refuses it in JSON, where 0.5.2 built a Python big integer or infinity. A vector set of scalar forms captured from 0.5.2 fixes the construction details, leading zeros included (ADR-002). A verdict that changes because Pydantic's lax mode coerced a value, where serde does not, is listed in the fixture. The plan confirms at the pinned version which event source gives scalar text and style: serde-saphyr's parser, or its parser crate added to the adapters allow-list by review. If neither does, the plan stops and asks.
4. **Strict JSON** (`src/orqlet/domain/strict_json.py` lines 14-52; A-14): input at most 1 MiB; UTF-8 only; duplicate keys, NaN and Infinity refused; the top level must be an object. New: an integer literal outside the signed and unsigned 64-bit ranges is refused as a number too long to read, where 0.5.2 refused integers only beyond Python's digit limit. New: a float literal outside the f64 range, such as `1e400`, is refused, where 0.5.2 accepted it as infinity; serde_json's own refusal is to be confirmed at the pinned version. Nesting is bounded by serde_json's built-in recursion limit, where 0.5.2 relied on Python's recursion limit. Both literal checks use a token scan before parsing; serde_json's `arbitrary_precision` feature is not used, because Cargo would turn it on for every crate in the workspace.
5. **TOML.** Every TOML input goes through the documents module behind a port: Cargo.toml and Cargo.lock for the technology and project scanners, `pyproject.toml` and TOML lockfiles for the dependency surface (`src/orqlet/domain/dependencies.py` lines 51-80), and model policy files (`src/orqlet/application/usecases/validate_model_policy.py` lines 605-627, 256 KiB). Each is UTF-8 and at most 1 MiB, or the caller's lower limit. The plan confirms the nesting behaviour of the `toml` crate and adds a depth check if it has none.
6. **Size limits bound the read.** New: every size limit on an untrusted file is enforced by reading at most the limit plus one byte through the FileSystem port. 0.5.2 read some files whole before comparing their size (`src/orqlet/adapters/scan/common.py` lines 39-40, `validate_model_policy.py` lines 608-610).
7. **Only the documents module parses.** Each crate's `clippy.toml` disallows the serde_json, serde-saphyr and toml entry points that read text or bytes: `from_str`, `from_slice`, `from_reader`, their `_with_options` forms and the `Deserializer::from_*` constructors. The documents module carries a scoped allow with a reason, and so may integration tests and the xtask, which parse their own fixtures and `cargo metadata` (ADR-001 decision 5). The list is a partial net; a parse through `str::parse` into a library value type is caught by the ORQLET-SEC-002 review.
8. **Messages never echo input** (A-12; `src/orqlet/application/contracts/loading.py` lines 1-27; `vcs.py` lines 41-56; `src/orqlet/application/usecases/resources_source.py` line 73 and `integrations_source.py` line 127). The documents module and the contract conversion turn every library error into a `location: rule` message without the offending value; credential checks and refusals report only the rule and the line. Library error text is never passed through. A value from the repository that a command shows on purpose, such as a path, a branch name or a commit subject, passes only through the filters of decision 15. New outside resources and integrations: an unknown key's name is left out, where 0.5.2 named it through Pydantic's error location (`loading.py` line 24). New: a duplicate key is refused without quoting it, where 0.5.2 quoted it (`yaml_loader.py` line 69, `src/orqlet/domain/strict_json.py` line 46). New (Q-20): a failed Git call gives ORQ-E106 with a fixed message naming only the allowed subcommand and the exit status, never Git's error output, where 0.5.2 quoted its first line (`git_runner.py` lines 132-136, `src/orqlet/adapters/git/vcs_git.py` lines 48-51).
9. **File system** (`src/orqlet/adapters/fs/local_fs.py` lines 1-10, 33-61, 110-149 and 186-215; A-19): every path is a CanonicalPath under the root. Every component is checked with `symlink_metadata` and refused if it is a symbolic link, or on Windows if it has `FILE_ATTRIBUTE_REPARSE_POINT` (0x400, defined in the module) set. Reads and replacements open the last component with `O_NOFOLLOW` on Unix, taken from the `libc` crate, a Unix-only dependency of `orqlet-adapters`. Temporary files are created with `create_new` beside the target under a name made of the process id and a counter, retried if the name exists, at most 100 times; they are synced, renamed into place, and then the folder is synced. On Unix a project write creates its temporary file with mode 0600 and gives it the target's existing mode, or 0644 for a new file, before the rename (lines 126-143). On Windows the rename is retried five times with a growing pause. The apply lock is opened through the same confined data-directory FileSystem. The check-then-open race on inner components stays, as in 0.5.2 (lines 7-10).
10. **Data directory.** It is `ORQLET_DATA_DIR`, else the OS local data folder plus `orqlet`; an empty variable counts as unset (`wiring.py` line 86). New (Q-16): it may not lie inside the repository. The check resolves the deepest existing ancestor of the data directory to its real path and appends the missing components, which may not be `.` or `..`. It compares the result, component by component and case-insensitively on macOS and Windows, with each of: the real project root; the real top level of the Git work tree, taken from the Vcs port (`vcs.py` lines 94-100 and 113); and, for a linked worktree (`vcs.py` lines 102-105), the parent of the common Git folder when that folder's name is exactly `.git`, or else the common folder itself, as for a bare repository or a separate Git folder. Accepted: with a separate Git folder the real main work tree is not compared, because `rev-parse` gives no bound for it without reading `core.worktree`; a hostile `.git` file can only cause refusals. The data directory, its `projects/<project id>/` and its `packets/` may not be any of these or lie inside one. A Vcs error other than "not a repository" is not read as "no repository" (`vcs_git.py` lines 66-84). Results per command:
    - The commands that write the data directory refuse before creating anything: ORQ-E105, exit 3, or ORQ-E106 for the Vcs error. They are the commands wired with the lifecycle services other than the three below, and `review prepare` (`wiring.py` lines 89-93, 158-162 and 200-223).
    - `doctor` and `sync` write nothing, and `explain` only shows (`src/orqlet/interface/cli/commands/lifecycle.py` lines 188, 203 and 243). New (Q-18): they report the same ORQ-E105 or ORQ-E106 as a finding, do not create the data directory, treat its data as missing, and go on.
    - `status` shows its existing not-run entry for user data (`src/orqlet/application/usecases/status.py` lines 43 and 228-229).
    - The hook starts no Git (`wiring.py` lines 119-140). New (Q-19): it prints `{}` when the data directory is the project root it finds by searching for `.orqlet/` (`hook_event.py` lines 92-102 and 220-233), or lies inside it.

    New: every project id, whether read from the profile or given as `rollback --project-id` (`lifecycle.py` lines 133-135, `src/orqlet/application/usecases/rollback.py` line 49), must be a lowercase hyphenated UUID, which makes it one path component. It is joined only through the confined data-directory FileSystem. Any other id is refused as a journal error, ORQ-E136, as `journal.py` lines 30-34 refuse an id that is not a path. New: the message names the id's source, the profile or `--project-id`, and leaves out the value, which 0.5.2 quoted (line 34).

    Test cases, each required by BC-23:
    1. A data directory in the project root, or below an ancestor that is a symbolic link resolving into it, makes a writing command refuse with ORQ-E105 and create nothing.
    2. A linked worktree with the data directory in the main work tree is refused.
    3. With a bare common folder, a data directory in that folder is refused and one in its parent is not.
    4. A Vcs error makes a writing command refuse with ORQ-E106.
    5. `doctor`, `sync` and `explain` report ORQ-E105, or ORQ-E106 on a Vcs error, create nothing and read no journal there, even a planted one.
    6. `status` shows its not-run entry and reads nothing from that data directory.
    7. The hook prints `{}` and exits 0.
    8. An empty `ORQLET_DATA_DIR` counts as unset.
    9. A project id that is not a UUID, from the profile or `--project-id`, is refused without the value in the message.

    New: on Unix, files the data directory gets are created with mode 0600 and folders with 0700, set at creation through `std::os::unix` options. 0.5.2 made only user-scope data private (`src/orqlet/adapters/fs/journal.py` lines 37-38) and wrote project journals, backups and review packets with default modes (`wiring.py` lines 158-162 and 198-224). 1.0.0 does not change the modes of folders it did not create.
11. **Journal** (`journal.py` lines 63-88). Paths read back from a journal on resume or rollback are parsed again as CanonicalPath and written only through the project FileSystem. 1.0.0 writes project journals where 0.5.2 does, `projects/<project id>/upgrade/<change id>.json` (`journal.py` lines 3-7 and 41-44), with 0.5.2's fields (lines 154-165) plus `format: orqlet-journal/1`; a record without `format` is a 0.x record. Every path that reads that folder reads each record's `format` and `status` first, through the documents module with the 1 MiB limit, as `open_changes` does (lines 79-88), and never rewrites a 0.x record. These paths are the upgrade guard, the supersede step of every journalled apply (`src/orqlet/application/usecases/apply_plan.py` lines 55-56), `doctor` and `sync` (`src/orqlet/application/usecases/diagnose.py` lines 398-409), resume and rollback. A `format` other than none or `orqlet-journal/1`, or a `status` other than `open`, `complete`, `superseded` and `rolled-back`, makes the record unreadable. New: so does a `change_id` that differs from the file name without `.json` (line 92), so advice only names an existing record.
    - Upgrade: an open 1.0.0 record refuses with ORQ-E131 and the advice of `src/orqlet/application/usecases/upgrade.py` lines 80-88 (`upgrade --resume` or `rollback`).
    - Any journalled apply, upgrade included: an open 0.x record refuses with ORQ-E131 and the advice to finish or roll it back with 0.5.2, before the apply takes the lock or saves a backup, with exit 3 as the upgrade refusal (`src/orqlet/interface/cli/exit_codes.py` line 10). This is new for the other commands, where 0.5.2 marked it superseded. Open 1.0.0 records are superseded as in 0.5.2.
    - `doctor` and `sync` report an open 1.0.0 record as ORQ-E170 with 0.5.2's advice, and an open 0.x record as ORQ-E170 with the advice to use 0.5.2.
    - An unreadable record refuses with ORQ-E136, exit 3, as 0.5.2 does (lines 70-77, `src/orqlet/interface/cli/errors.py` line 19, `src/orqlet/interface/cli/runner.py` line 33); its message names the file, which the person inspects and removes.
    - Resuming or rolling back a 0.x record is refused with ORQ-E136.
    - `complete`, `superseded` and `rolled-back` records are ignored.

     A 0.x journal under a different data directory (U-10) is not seen; the rule that the two binaries never run on one project covers that case.
12. **Hook** (`src/orqlet/interface/cli/commands/hook.py` lines 38-48): standard input is read up to the payload limit plus one byte. Any error, including a panic caught with `catch_unwind`, prints `{}` and exits 0. The release profile pins `panic = "unwind"` and the 2 s deadline stays (`wiring.py` line 52). Every command, the hook included, installs a panic hook that prints nothing; outside the hook a panic gives ORQ-E900 with the fixed message `internal error`, never the panic payload, as `runner.py` lines 34-35 report only an exception's type name.
13. **Rust project scanner.** It reads only the scope's Cargo.toml and Cargo.lock and the member manifests named below, through the FileSystem port, at most 1 MiB each, as UTF-8. It never runs cargo or rustc and never follows `path` dependencies or `[[bin]] path` entries. Workspace members are followed only when written as literal paths without glob characters, at most 32 of them, each parsed as a CanonicalPath under the scope. `rust-version` is accepted only if it matches `^[0-9]{1,3}(\.[0-9]{1,3}){0,2}$`. Frameworks come only from the known-crate table `CRATES`, as in `src/orqlet/adapters/scan/technology_scanners.py` lines 190-225.
14. **Paths** (`src/orqlet/domain/paths.py` lines 17-48; A-15): CanonicalPath refuses empty, `.` and `..` components; characters of the categories Cc, Cf and Cs; backslash and colon; a trailing dot or space; components over 255 bytes; Windows device names before the first dot; and any component that folds to `.git`. The domain gets Unicode category data from a pinned no_std crate on its allow-list. The candidate `unicode-general-category` was not looked up; the plan confirms it at the pinned version, including the categories Co, Cn, Zl and Zp that decision 15 needs, and stops and asks if it does not fit.
15. **Output filters.** Text from the repository that Orqlet shows passes one of two domain filters, carried over from 0.5.2, and the escaping filter is applied more widely (Q-21):
    - **All or nothing**, for anything that reaches an IDE agent's context or `status` (`src/orqlet/domain/representable.py` lines 1-62). A version is shown only when it is an ASCII `major.minor.patch` that parses as a Version. The Rust Version keeps unbounded parts as decimal text without leading zeros (`versions.py` line 11), compared by length and then text; a part over 4,300 digits is refused, as Python's default integer limit makes line 51 do. A path is shown only when it holds 1 to 200 Unicode scalar values, as Python's `len` counts, and none is hidden; text from Git is decoded as strict UTF-8, as `vcs_git.py` line 77 does, never with replacement characters. Hidden means the categories Cc, Cf, Cs, Co, Cn, Zl and Zp, plus the ranges of lines 24-35 (variation selectors, Hangul fillers, the Braille blank, the combining grapheme joiner, the Khmer inherent vowels and the Mongolian selectors). Anything else is dropped, never repaired. The users are the hook's session-start context (`src/orqlet/application/usecases/hook_event.py` lines 110-121, with the project version read from `.orqlet/workflow.lock`, and the whole text dropped when longer than `MAX_STATUS_CHARACTERS = 1200`, lines 38 and 121), its post-edit context (lines 161-166), `status` (`status.py` lines 174 and 221) and the user-scope reader (`src/orqlet/application/contracts/user_scope.py` line 27).
    - **Escaped** (`src/orqlet/domain/conventions.py` lines 100-124). Every character outside printable ASCII is written as `\xNN`, `\uNNNN` or `\UNNNNNNNN`, a backslash is doubled, and the result is cut at the caller's limit and then ends in `...`. New (Q-21): every repository-controlled value in a finding, a not-run entry or a refusal is either left out (decision 8) or passed through this filter, with a limit of 200 where 0.5.2 gives none, and is never formatted with `Debug` or `Display`. This replaces the raw and Python `repr` forms of 0.5.2, for example `validate_design.py` lines 127 and 130, `validate_records.py` lines 607, 619 and 647, and `paths.py` lines 32-47. The 0.5.2 users keep their limits: branch names and commit subjects (`conventions_check.py` lines 181 and 195), evidence paths (`validate_as_is.py` line 155, `evidence_cite.py` line 160), model-policy reasons (`validate_model_policy.py` lines 218, 268 and 379), and resource and integration paths (`validate_resources.py` lines 52, 71, 157 and 160; `validate_integrations.py` lines 92 and 110; `resources_view.py` lines 76 and 103). The change id in the advice of ORQ-E131 and ORQ-E170 passes it too.
    The filters live in `crates/orqlet-domain/src/representable.rs` and `crates/orqlet-domain/src/conventions.rs`. The Unicode version behind Cn follows the pinned crate, so a character unassigned in one version and assigned in the other is filtered differently from 0.5.2 (U-8).

## Consequences

- Each rule above has a criterion in the brief (BC-6, BC-7, BC-17 to BC-24), so a missing rule fails a test instead of passing review.
- Two dependencies are added for security: `libc` (Unix only, adapters) and a Unicode category crate (domain). Both are on allow-lists that a reviewed change edits.
- With process creation private to the Git module, names need no matching: `GIT`, `/usr/bin/git` and wrappers such as `env git` have no way past GitRunner.
- Reading YAML through a generic tree costs one conversion step, but keeps 0.5.2's resolver exactly, so booleans and numbers keep their 0.5.2 types.
- A data directory inside the repository, and a project id that is not a UUID, both accepted by 0.5.2, stop working in 1.0.0; the release notes say so.
- A 1.0.0 journal stays readable by 0.5.2, which ignores the extra `format` field, but the two binaries still never run on one project.
- On Linux and Windows the controls are compiled and linted but never run (Q-15), so the Windows reparse-point check and the rename retries ship untested.

## Rejected alternatives

- A public ProcessRunner that refuses `git` by name: it needs rules for case, paths, extensions and wrappers, and no shipped caller needs a public entry.
- Parsing YAML straight into the contract types: the key type, tag and scalar style are gone before the 0.5.2 rules can be checked.
- A separate journal folder for 1.0.0 records: the guard and rollback would search two folders, where one field tells the versions apart in the folder 0.5.2 already uses.
- Hard-coded `O_NOFOLLOW` values per target: avoids one crate, but the values differ between Linux and macOS and are easy to get wrong.
- Reading integers outside 64 bits as floats: silently changes values that a later write could store.
- Passing library error text through: serde messages may quote the value, which can be a secret pasted into the wrong file.
