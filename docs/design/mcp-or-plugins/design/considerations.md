## Security (affected)

| Threat | How the design holds it | What is left |
|---|---|---|
| A credential is written into a committed MCP file or the declaration | The contract cannot name a shared identity; the entry has no credential field; the scan runs on the declaration, on rendered text and in every check, on raw text and on decoded strings (ADR-002 decisions 1, 5, 7) | A credential shape the scan does not know, or one that someone encoded on purpose |
| A credential is redirected to another host | The address is a literal on an exact-string table in the tool, not in the adopter's pull request; no `env-ref` row exists in this change (ADR-002 decisions 2 and 4) | An adopter who patches the tool or the check |
| A pull request quietly edits the entry | The pin: `entry_differences` against `rendered_entry`; undeclared `orqlet-*` entries, closed keys and the text `${` are errors; the counts of undeclared entries are printed (decision 6) | Another undeclared entry that starts a process or reaches a server without a reference is left alone; the Codex file gets the scan only |
| A personal same-name entry shadows the project entry | The `orqlet-` prefix keeps Orqlet's names apart; check V-4 records which entry wins | Orqlet does not read personal files (A-35, A-53) |
| The user's own value is exposed on the machine | Nothing in this change creates a value. The README gives the instruction; V-8 records where a value can leak | The client's handling |
| Untrusted files crash or fool the checks | Strict loader, size and nesting caps, duplicate keys rejected, fail-closed findings, a link or unreadable file is an error (decision 8) | Whether the clients' readers agree with the validator on comments, escapes and key case (V-9); the whole-file read before the size check, as in the registry |
| A proposal copies a credential from the team's file into a new file | `_Builder._propose` passes no existing bytes for the MCP path of any client, compared on the case-folded key (ADR-003 decision 5); nothing depends on the scan or on an adapter remembering a flag | A team whose file holds its own servers sees a proposal item on every run until it merges the text; a profile that names an MCP path as a pull-request template target is outside this design |
| The check is switched off by deleting the declaration | `validate` is not run (exit 5) and `doctor` and `sync` warn when an MCP file holds the text `orqlet-` (decision 11) | A pull request that deletes the declaration and renames the entries in one change, or edits the CI job or the pinned tool version, is stopped only by review |
| An unattended surface serves several people with one identity | Q-12: the surface uses the account of the one user who started or owns it; V-10 asks whether the clients can | Where they cannot, the standard is not met there, in every mode |
| The Atlassian entry gives the agent more than the label says, and text it reads can steer its actions | The labels are made honest as far as the contract allows and an information finding says the user's full permissions apply (decision 10); V-10 asks whether scopes can be limited | The contract forces the two labels; a prompt-injection path through server content is not limited by the entry |
| The review of this repository is advisory | Disclosed: no `CODEOWNERS`, protection returned HTTP 403 (`github-state.yaml:26-31`); ORQ-I030 lists the paths (ADR-003 decision 8) | Without a required review and a required check, a pull request can switch the check off |
| Routes that bypass the files (managed settings, plugins a committed settings file enables, other keys of the Codex file, a shared human-signed account) | Not examined; listed in ADR-002 decision 12 | Stated limits |

No new dependency, no network access, no secret and no new process is introduced. One existing behaviour is outside this design: `orqlet review prepare` copies the staged tree into a packet outside the repository without a scan. Every write goes through the journalled change plan (ORQLET-SAFE-001); every process still goes through the ports (ORQLET-SEC-001). No digest is introduced; the existing ones are SHA-256 (ORQLET-SEC-003).

## Compatibility (affected)

- **Contract.** `orqlet.integrations/v1` is tightened in place (Q-13). A hand-written declaration elsewhere could become invalid, and `upgrade` then refuses until it is fixed; none is known. The valid fixture is updated. The committed JSON Schema does not change.
- **Python surface.** `compose` gains a keyword parameter with a default and `RenderRequest` gains an optional field with a default. Existing callers keep working. Eight public names are added and three are changed (the component view); the proposal files for the three MCP paths change in content.
- **Generated files.** `.mcp.json` is a new seeded file and is written only when a declaration exists, a server is registered for Claude Code and the profile enables it. A project without a declaration keeps its files unchanged. The lock records the file with owner `seeded` when Orqlet wrote it; a team's own differing file is never recorded, and gets a proposal with the wanted text only.
- **`doctor` output.** For every project the ORQ-I030 list gains `.mcp.json`, so the tests that pin it change; for a project without a declaration, `doctor` and `sync` warn when an MCP file holds the text `orqlet-`.
- **Workflow package.** The rule text and its meta file change, so the manifest digest changes, and the version is bumped in the same step (0.3.3 proposed, because 0.3.2 is taken). The golden files of the three clients are regenerated once; the Claude Code and Cursor ones change through the rule text and all three through the version marker. This repository's design and plan headers go stale when the person runs `orqlet upgrade` (ORQ-W390).
- **Finding codes.** The families `ORQ-E530` to `ORQ-E539`, `ORQ-W530` to `ORQ-W539` and `ORQ-I530` to `ORQ-I539` are unused today.
- **Python and dependencies.** 3.12 to 3.15 as today; `pyproject.toml` and `uv.lock` do not change. The standard-library `tomllib` is not used in this change.
- **The plan that this design replaces.** Its phase P-1 (the domain module) is on `main` and is kept. Its later phases, its acceptance criteria and its codes are replaced by a new plan.

## Operations (affected)

- **New command.** `orqlet validate integrations [file]`. `doctor` and `sync` run the same checks. The adopter adds the command to their CI with a pinned tool version (ADR-002 decision 11). CI in this repository is unchanged, because this repository has no declaration.
- **Checks with test accounts.** Ten checks are specified, performed by a person and recorded as files (ADR-004). Six of them (V-1, V-5 and V-9 for Claude Code, V-4, V-6, V-10) are a phase of this change's plan; the other four are paid by the release that needs them.
- **Rollback.** Revert the commit, or `orqlet rollback` for what `upgrade` wrote. A team that wants no MCP file takes it over: it deletes the declaration and renames or removes the `orqlet-*` entries, because while an `orqlet-` name remains `doctor` and `sync` warn that nothing is checked, and a warning exits 1.
- **Failure behaviour.** An invalid declaration stops `upgrade` with exit 3 before anything is written. The read-only checks exit 5.
- **Observability.** Findings carry rule ids, line numbers and closed field names. Nothing is logged that holds a value.
- **Cost.** One more small read in `upgrade`, `doctor` and `sync` when a declaration exists, and up to three small file reads when it does not.
