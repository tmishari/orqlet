# Considerations: security, compatibility, operations

## Security

- **A credential in the repository.** The contract refuses a variable name that is not a name, an address with user information, a query or a variable, a mode that the closed table does not enable for the address and client, and an identity label that does not match the mode. The scan runs on raw text and on decoded values (JSON and TOML escapes, YAML scalars) and reports literal tokens, user information and credential-named query parameters in a URL, a literal `Authorization` value and a credential-named key with a literal value. It runs on the declaration, on rendered text before it is written, on every planned proposal of an MCP file before the plan is returned, and on each MCP file in the read-only checks; it reports line numbers and rule names, never values or raw keys (ADR-002 decisions 7 to 9). The scan is a floor: a token shape it does not know passes, which is why the closed key sets, the value grammar and the pin comparison exist as well.
- **Another user's credential.** Not enforceable by Orqlet. The design removes the routes that it can detect in the repository and that make one credential serve many users: service-account key, team plugin variable, Team MCP credential, helper commands, static client secrets, and (when `env-ref` is enabled) a variable assigned in a committed file (ADR-002 decisions 5, 6 and 10). Routes in committed files that it does not examine: plugins and marketplaces that a committed `.claude/settings.json` enables (A-85, A-87), plugin settings in a project `.codex/config.toml` (A-103), hooks, `env` or helper commands in `.claude/settings.json`, an undeclared entry that starts a process or reaches a server with no reference, and an undeclared entry that shadows a personal entry of the same name in Cursor or Codex. Routes outside the repository, which Orqlet cannot see: a managed or cloud-managed configuration that an administrator sets (A-67, A-106), Cursor Team MCP servers and team plugin variables (A-114, A-115), a variable that CI or a cloud agent environment shares between several people, and a lent token or shell. A project with no declaration is not checked, and deleting the declaration switches the checks off: `validate integrations` then returns not run, and `doctor` reports a check that did not run when the lock records an MCP file. The vendor's own audit is the only place where that shows (ADR-002 decision 13).
- **Entries that Orqlet did not generate.** Orqlet checks a declared entry exactly, rejects an undeclared `orqlet-*` entry (in any letter case), and rejects an undeclared entry that holds a variable reference, a key of the closed credential list (ADR-002 decision 6) or a literal credential. It leaves other undeclared entries alone, inline servers in agent files and MCP files in nested or parent folders unexamined, so an undeclared entry that starts a process (`command`, `args`) or reaches a server with no reference is **not judged**. Only people reviewing the pull request, and the client's own approval prompt (not relied on until V-1, V-3 and V-4), cover that case (ADR-002 decision 6).
- **Unattended surfaces.** Q-7 lists cloud agents, web sessions and code-review contexts, and CI runs the same way. The person's answer to Q-12 is that such a surface uses the account of the one user who started or owns it. The evidence does not say whether the clients can do that on each surface (check V-12). Where a surface cannot be bound to one user, or runs in an environment that several people share, Q-6 and Q-9 are **not met** there for any mode, OAuth included, because whichever identity it holds serves everyone who triggers it, and the vendor itself markets API-token use for CI and bots (evidence `atlassian-rovo-mcp.md:10,23,31`). Such a surface is a written gap and gets no entry.
- **Read-only labels are not enforced.** The declaration says `read-only`, `deny` and `enforced_by: server`; the generated Atlassian entry restricts no tool, the OAuth consent decides the scopes, and release 1 therefore gives the agent the user's full Atlassian permissions as consented. The evidence leaves open whether a grant belongs to a client or a user (U-10), what the domain allowlists govern (U-11) and the site limits (U-12); V-13 asks about scope pins. `validate integrations` and `doctor` print an information finding and the README says so, so that a reviewer does not read the labels as a control.
- **Redirection of a credential.** `Authorization: Bearer ${NAME}` pointed at another host would send the user's value there. The address is a literal on a closed table (ADR-002 decision 2), the file is compared with the entry that the tool builds from the declaration, and a changed address with an unchanged variable name is an error. The offline comparison cannot tell a consistent change among combinations that the table allows (in release 1 the table has one row, so only renames and removals remain); only review catches it, and the comparison against the target branch needs `ci check`, which is not built (A-14, A-15). V-8 records whether a client asks before connecting to a changed address, and `env-ref` stays off for a client until that is known (ADR-004 decision 2). V-10 records whether a stored OAuth token follows an address change; Codex and Cursor OAuth entries wait for it.
- **The anchor depends on where the check runs.** The pin is independent of the declaration only if the validator runs from reviewed sources. A pull request that edits the workflow that runs it, the pinned tool version, `.claude/settings.json` or `CODEOWNERS` can switch the check off. `doctor` reports when no `CODEOWNERS` file mentions these paths (a mention, not proof of an effective review), and without a required review and a required status check on the host the control is advisory (ADR-002 decision 11).
- **Review cannot be enforced here today.** Q-11 names this repository's code owners as the reviewers. At the base revision this repository has no `CODEOWNERS` file, and the earlier capture of GitHub (open-items evidence, not refreshed since) shows one collaborator and a refusal of branch protection and rulesets with HTTP 403 (`github-state.yaml:26-31,38-41`), so a "code-owner review" there would be a review by the same person. A `CODEOWNERS` file is advisory without a required-review rule. Whether GitHub enforces it depends on a plan or visibility change that is not decided here.
- **A secret copied through a proposal.** A proposal is a diff of the whole existing file. Orqlet refuses a planned proposal for a file that is not tracked or that the scan flags, before the plan is returned; a file that Orqlet wrote or that equals the render yields no proposal and is not refused. A tracked file with uncommitted local edits that hold a credential of a shape the scan does not know would still be copied; that residual risk is stated for the person to accept (ADR-003 decision 3).
- **Same-name entries in both directions.** A user can define an entry with the same name in a personal scope and it may win (the architecture document states that Claude Code resolves local before project, A-20). In the other direction, Cursor's project config takes priority over global and both files are merged (A-109), and Codex project configuration outranks user (A-104); whether a merge is per field is not stated, so a committed entry with a hostile address and the name of a personal entry could inherit the user's personal header or variable. Orqlet cannot prevent either case with a committed file. V-3, V-4 and V-6 record the behaviour, and Codex and Cursor entries are not generated before V-3 or V-4.
- **Approval and trust steps are client behaviour.** Whether a client asks before connecting, and again after a change, is not stated by the accepted evidence for all three clients; V-1, V-3, V-4 and V-8 record it, and `env-ref` entries are not generated for a client until they exist. Until then the design does not rely on a prompt.
- **A variable that is not set.** Codex may connect without authentication (A-94). The other clients' behaviour is recorded in V-2 and V-3. What the server does with a missing credential is not stated; no other user's value is used.
- **Exposure of the user's own value.** A variable can reach child processes, agent shell tools, logs or telemetry, and desktop apps started outside a shell may not see it at all (V-9). The README instruction for `env-ref` is written after V-9.
- **Sign-in storage.** Codex stores MCP sign-ins in a keyring or a file (A-98); for Claude Code and Cursor the accepted evidence does not name where MCP sign-ins are stored (A-74 does not name MCP servers), and V-5 records it. Orqlet does not read any of them (A-53).
- **Untrusted files and bounded input.** The committed MCP files and the declaration are untrusted input (ORQLET-SEC-002): they are read through the `FileSystem` port, parsed with the strict YAML loader, a duplicate-key-rejecting `json` reader and `tomllib` only, never executed or evaluated. A file above 256 KiB, nesting above 16 levels, more than 64 entries or a string above 2048 characters is refused, and the scan reads at most 4096 characters per line with bounded patterns, and a longer line or value is itself a finding (ADR-002 decisions 7 and 8). V-11 compares these parsers with the clients'.
- **Fixtures.** Test fixtures use obvious placeholders only (ORQLET-SEC-003). Negative tests build credential-shaped text from parts so that the repository never contains a real-looking token. Check records of ADR-004 are scanned before they are committed.
- **Digests** in new code use SHA-256 only (ORQLET-SEC-003). No certificate, TLS setting or cryptographic primitive is added.
- **Security-relevant paths.** The manifest lists `security_globs` for the credential-handling files and declares them in a `security` expected change, so the class stays D3 even if the declared trust boundary were removed.

## Compatibility

- `orqlet.integrations/v1` is tightened in place. In this repository no module reads it and no declaration exists (AS-IS A-13); whether another project holds one is not known, and a declaration has no effect today. The architecture document's versioning rule calls a breaking schema change major with a migration (Section 20.2), so this is a waiver, which the person accepted on 2026-10-26 (Q-13). The existing valid fixture `tests/fixtures/contracts/valid/orqlet.integrations.v1.yaml` fails the new rules and is updated with its tests in phase 2.
- The MCP files are written only when `.orqlet/integrations.yaml` exists, and then as seeded files: a file that already exists is not rewritten, a change arrives as a proposal (a whole-file diff), a deleted file does not come back. Existing projects see no new file. This change generates one entry kind: Atlassian OAuth for Claude Code in `.mcp.json`.
- The client adapters' output for existing files does not change, but the workflow version bump of ADR-003 changes the markers of the generated files, so the goldens that carry the version are regenerated once on purpose, and a new golden is added for `.mcp.json`.
- The protected workflow package changes in two files: the rule text `orqlet-workflow.md` and its meta file; the contract rules are validators, so the committed schema does not change. The release steps (manifest rebuild, identity bump, release record, `versions.yaml` proposal, `orqlet upgrade`) follow, and this task's own design and plan headers become stale for `workflow_version` and `protected_set_digest` when the person runs `orqlet upgrade` in this repository, the last step of the plan (ORQ-W390).
- Recorded seeded files keep proposing after a declaration change (ADR-003 decision 9).
- The lock gains an entry for `.mcp.json` when it is written; `orqlet rollback` restores it through the journal.
- The architecture document is aligned with the built contract and with the decision on plugins (Section 4.8 conclusion unchanged: plugins later) and with the Miro exception of ADR-001.
- No new dependency; Python 3.12 to 3.15 and the three platforms are unchanged.
- Miro is not generated and its plugin or manual entry stays the user's own (ADR-001 decision 5); this is a stated exception to "the same configuration for everyone", and the person may reject it in the design pull request.

## Operations

- A new command, `orqlet validate integrations <file>`, returns the usual verdicts (exit 0, 5) and the JSON envelope; `init`, `upgrade` and `explain` refuse with exit 3 on an invalid declaration. CI is unchanged and the new tests run in the existing `tests` job. Adopters add the command to their own CI (README).
- `orqlet doctor` and `orqlet sync` run the same checks on the committed MCP files, because a seeded file is invisible to hash drift (the code skips `SEEDED` entries, `diagnose.py:72-73`). A check that cannot run (no commit, a failing Git call) is reported as not run.
- The thirteen checks of ADR-004 are done by a person with test accounts and recorded as files. Orqlet cannot run them.
- Rollback: revert the commit, or `orqlet rollback` for files that `upgrade` wrote.
- Orqlet starts no process of its own, opens no socket and reads no environment variable for this feature: the scan and the comparison work on text, and Git runs only through the hardened `Vcs` port.
- Recovery text for a failed rule names the rule and the field, so a maintainer can fix the declaration without seeing a secret.

## How the standards apply

- ORQLET-ARCH-001, ARCH-002, ARCH-003: the layer table of the component view; the schema file is read-only data and no domain or application module imports `orqlet.workflow`.
- ORQLET-DET-001: `render_mcp_file` writes no timestamp, path or random value, and fixes the key order (ADR-003 decision 6); the new golden is changed only on purpose.
- ORQLET-DET-002 and DET-003: `MANIFEST.json` is rebuilt and the package version is bumped because the rule text changes; the committed schema is unchanged and `tools/export_schemas.py --check` passes (ADR-003 decision 8).
- ORQLET-SAFE-001 and TEST-002: the new file is written only through the existing journalled change plan; `apply_plan.py` is not changed, and a fault test covers a run that writes the new seeded file, stops after each step and converges on a re-run (including an untracked file that Orqlet wrote).
- ORQLET-NOMODEL-001: no model call, no agent start, no network access (Operations).
- ORQLET-SEC-001: no process is started except Git through the `Vcs` port. ORQLET-SEC-002 and SEC-003: see the Security section.
- ORQLET-QA-001, TEST-001, STYLE-001: ruff, strict mypy, import-linter and the full suite pass before the pull request is ready; behaviour is tested with the repository's fakes and no network.

## Open decisions that this design leaves to the person

- **Miro** has no generated entry (ADR-001 decision 5).

## Validation and rollback of the design itself

- Tests: unit tests for every rule of the contract with a failing and a passing case; unit tests for the scan with credential-shaped text assembled from parts and with look-alikes that must pass, a trailing newline and U+212A; a property test that the scan's result and every message never contain the matched text, key or value; a worst-case-time test; a test that renders each shape and validates it, then mutates each field; contract tests for the schema; a golden test for `.mcp.json`; integration tests for `validate integrations`, for `doctor` and `sync`, for the untracked and flagged existing file before a proposal, and for the seeded-file behaviour of `upgrade`.
- Rollback is a revert of the pull request; no persisted state outside the files.
