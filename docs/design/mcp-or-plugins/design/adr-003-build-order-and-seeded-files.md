# ADR-003: Validators before renderers; the MCP files are seeded files that change only by proposal; scope of this change

Status: proposed. It becomes accepted when the design pull request is merged by an authorised person.

## Context

- Nothing generates, reads or scans an MCP or plugin file today. The contract exists and is unused, the three client adapters render no MCP file, and the CLI has no `mcp` command (AS-IS A-1, A-2, A-3, A-6, A-13). The README and Section 22.0 say that the MCP generators, `ci check` and the hooks are not built (A-14, A-15), and Milestone M4 holds the MCP work, with the 1.0 plugin packaging later (A-16, A-17).
- Ownership. A `shared-entry` ownership mode is defined and a lock entry in it must name its entry, but no adapter sets an entry name (A-4, A-5). The design's earlier plan edits only `orqlet-*` entries inside shared JSON and TOML files (A-31). Orqlet has no TOML writer beyond flat tables (`src/orqlet/adapters/render/emit.py:97-115`) and no TOML round-trip library has been chosen (AS-IS unknown under Q-8).
- The existing `SEEDED` mode (`src/orqlet/domain/classify.py:65-74`, `src/orqlet/domain/changeplan.py:371-397`):
 - a file that is absent and has no record is written;
 - a file that is present, has no record and differs from the render becomes a proposal, and equals the render once the team has applied it, which records it;
 - a deleted recorded file is never brought back;
 - for a **recorded** file that is present, the state is a proposal whenever the new render differs from the **recorded** text, whatever the file holds now (`classify.py:74`), and the record does not advance while the state is a proposal (`changeplan.py:386-397`). So after the declaration changes, every later `upgrade` writes a proposal again, even when the team has applied the earlier one by hand.
 - A proposal is a unified diff of the whole file under `.orqlet/proposals/`, with three lines of context (`changeplan.py:371-384`, `:440-441`), so text that the file held appears in it. The other seeded files (`versions.yaml`, the profile) are recorded with no file class.
- `doctor` measures drift for generated files only; a `SEEDED` file is never reported as drifted (`src/orqlet/application/usecases/diagnose.py:72-73`). `doctor` and `sync` share one diagnosis (`_diagnose`, `diagnose.py:108`; the wrappers are at `:60-65`). The CI check against the target branch is not built (A-14, A-15), `.github/workflows/ci.yml` runs no `orqlet` command, and this repository's GitHub plan refused branch protection and rulesets with HTTP 403 at the time of the capture (open-items evidence `github-state.yaml:26-31`).
- Exit codes. `REFUSED` (3) is "invalid input, unsafe state or a rule that forbids it" and is what `init`, `upgrade` and `explain` return when composition raises; `CHECK_FAILED` (5) is the verdict of a read-only check, and `validate` commands return it on a FAIL (`src/orqlet/interface/cli/exit_codes.py:10-13`, `commands/validate.py:44`).
- Many facts about client behaviour are not stated (the unknowns under Q-8); the answer to Q-8 allows checks with test accounts.
- Compose (`render_all.py:116-125`) holds `Services` while the validators hold `ValidateServices`, and the adapters receive only a `RenderRequest` (`instruction_adapter.py:80-92`). The existing files are read in `plan_changes` (`render_all.py:327-352`), which `init` and `upgrade` call and `explain` does not. `Services` carries a `Vcs` port with `tracked_files()` and `read_committed()`.
- The workflow rule text that every adopter receives says that `.mcp.json` is "generated by Orqlet" and must not be edited by hand (`src/orqlet/workflow/rules/orqlet-workflow.md:3-6`; paths in `orqlet-workflow.meta.yaml`); it describes a file that Orqlet owns, which a seeded file is not (AS-IS contradiction C-4, unknown U-79).

## Decision

1. **Order.** Phase order for the plan: (1) the pure module `mcp_credentials` with its negative tests, because the contract's validators call it; (2) the contract rules (validators calling `name_problems`; the committed JSON Schema does not change), `Integrations.registered_for`, the update of the existing valid fixture and the workflow-package edits of decision 8, with the golden files that the rule-text edit changes regenerated on purpose; (3) `load_integrations`, `orqlet validate integrations` and the `doctor` and `sync` hook (the committed-assignment check waits for the release that enables `env-ref`); (4) the renderer, the Claude Code adapter, compose and the `plan_changes` hook; (5) the documents, the README section for adopters and the `CODEOWNERS` entries; (6) last, the person runs `orqlet upgrade` in this repository. The renderer is not built before the validator that checks its output. This change builds and generates **one entry kind**: Atlassian OAuth for Claude Code (ADR-002 decision 2). The other shapes and rows wait for the checks of ADR-004 and a later release that enables them with their own tests.
2. **Seeded files, no entry-level editing.** `.mcp.json`, `.cursor/mcp.json` and `.codex/config.toml` are written as complete texts holding only the generated entries, recorded with owner `seeded` and no file class. The `shared-entry` mode stays unused and no TOML library is added. A team that already has such a file is never rewritten: it gets a proposal, which is a full-file diff and shows the team's own servers as removals. In this change only `.mcp.json` is generated.
3. **No leak through a proposal.** `plan_changes` owns this step. After `build_plan` has produced the plan and before `plan_changes` returns it, each planned proposal for an MCP path (the paths come from `mcp_file_path`, so no declaration is needed here) must come from a tracked file (`Vcs.tracked_files()`; a project that is not a Git repository, or a failing call, counts as untracked) and its text must pass the scan of ADR-002. Otherwise the run is refused (`InitRefused`, exit 3), the plan is discarded, nothing is written or previewed, and only rule names and line numbers are printed. A file that Orqlet wrote itself, or that already equals the render, produces no proposal and is never refused, so a re-run, `--resume` or `--check` before the commit converges and an interrupted run (file written, lock not yet) classifies the file as up to date. `explain` does not call `plan_changes`; it scans only the rendered text. Residual risk, stated for the person to accept: a tracked file with uncommitted local edits that hold a credential of a shape the scan does not know would still be copied into a proposal.
4. **Only when a declaration exists.** If `.orqlet/integrations.yaml` is absent, `init` and `upgrade` write no MCP file and `doctor` and `sync` skip the checks. This repository gets none from this change.
5. **The seam.** `load_integrations(project, loader, path)` is the one function that owns the three declaration checks: the strict load and contract validation (including `name_problems`), the closed table (`allowed_auth_modes`) and the scan of the declaration. It maps errors to rule ids and closed field names (ADR-002 decision 9) and returns the declaration with `Finding`s: an absent file gives `(None, ())`, an invalid one gives `(None, findings)` with at least one error, and a valid one gives the declaration. The public constant `DECLARATION_PATH` (`.orqlet/integrations.yaml`) is passed by compose, by `_diagnose` and by `validate_integrations`; the file argument of `validate integrations` must equal it, or the result is a failure. New error codes are registered in the way of the existing ORQ codes, and the plan names them; ERROR severity gives exit 5 for the read-only checks. Compose and `validate_integrations` both call it, so exit 3 and exit 5 come from one implementation; `_diagnose` builds a `ValidateServices` from the `project`, `vcs`, `loader` and `workflow` of its `Services` and calls `validate_integrations`. Compose calls it with its own `Services` and attaches the declaration to the request with `dataclasses.replace`; `plan_changes` keeps its signature and needs no declaration (decision 3); `RenderRequest` gains an optional field `integrations` and `build_render_request` (`render_request.py`) keeps its signature. A declaration that is present but invalid makes `init`, `upgrade` and `explain` refuse with exit 3, naming the rule (`explain` shares compose and writes nothing); for `init` and `upgrade` nothing is written, and the other generated files are not written either, so that a half-applied security setting never exists. The Claude Code adapter calls `render_mcp_file(servers, client)` with `Integrations.registered_for(client)`; the other two adapters ignore the field in this change. Compose renders only for clients that the profile enables, and `validate integrations` and `doctor` have no profile, so they check a client's MCP file only if it exists: an absent file is an information finding, not an error, and an existing file that lacks a declared entry is an error. A team that deletes the seeded file does not get it back (`classify.py:72-73`); recreating it is the team's manual step, and this change adds no command for it.
6. **Outputs.** `render_mcp_file` returns the text of one client's file by writing what `rendered_entry` returns: for Claude Code, `{"mcpServers": {"orqlet-<id>": {"type": "http", "url": "<address>"}}}` with keys in insertion order, `json.dumps` with an indent of two and a trailing newline (the shape of the vendor's example, evidence `claude-code-mcp.md:38-43`; V-1 confirms it for the Atlassian address) (no new public name in `emit.py`; no timestamp, path or random value, ORQLET-DET-001). The Cursor shape, the Codex shape (`[mcp_servers.orqlet-<id>]`, trusted projects only; A-18, A-30, A-91, A-108, A-110) and the `env-ref` headers are specified in ADR-002 decision 5 and are built by the release that enables them. A declaration that asks for a mode that the closed table does not enable for that address and client is an error; entries keep `verification: not-tested` until the check records exist.
7. **`doctor`, `sync` and CI.** `_diagnose` (`diagnose.py:108`) runs the checks of `validate integrations` whenever a declaration exists and reports their findings, plus an information finding when no `CODEOWNERS` file mentions the paths of ADR-002 decision 11. A failing `tracked_files` or `read_committed` call, or a repository with no commit, is reported as a check that did not run, not as an error. The hash checks do not see seeded files, so this is the only drift check for them. `.github/workflows/ci.yml` is not changed here (it runs no `orqlet` command; `ci.yml:1-107`): the new tests run in the existing `tests` job; the README gives adopters the line `orqlet validate integrations .orqlet/integrations.yaml` for their own CI until `ci check` exists, says that the tool must be installed at a pinned version from a reviewed source, that only this command checks the rules, and that the read-only labels of the declaration are not enforced by the entry. The comparison against the target branch (stage 2 of `ci check`) stays designed and not built (A-14, A-15). The `.github/CODEOWNERS` file of this repository covers the credential-handling sources, the workflow package and these design files; adopters get the list of ADR-002 decision 11.
8. **The protected workflow package.** The change touches the package in two files: the rule text `rules/orqlet-workflow.md` and its `rules/orqlet-workflow.meta.yaml`, which stop calling `.mcp.json` a file that Orqlet owns. The contract rules are validators, so the committed schema `orqlet.integrations.v1.json` does not change and the check `tools/export_schemas.py --check` passes as it is (ORQLET-DET-003). The new text says that the MCP files were seeded by Orqlet and belong to the team afterwards, that changes arrive as proposals, and that a file may name variables but never hold a credential value. The manifest is rebuilt (`tools/build_manifest.py --check` runs in CI), and `identity.json` is bumped before release (ORQLET-DET-002) to a version number that the person chooses. Whether and when to record the release in `releases.json` is the person's decision at release time. The approvals of this task become stale (`workflow_version`, `protected_set_digest`, ORQ-W390) when the person runs `orqlet upgrade` in this repository, which is why it is the last step of the plan; the change to `.orqlet/versions.yaml` arrives as a proposal, and the plan carries a step for the person to re-approve the design and the plan.
9. **Recorded seeded files keep their proposal state.** After a declaration changes, a recorded MCP file stays in proposal state on every `upgrade`, even when the team has applied the proposal by hand (Context); there is one proposal path per file and it is rewritten only when its text differs (`changeplan.py:148-155`, `:371-382`). A proposal shows the team's own servers as removals, so applying it verbatim would delete them; the team merges by hand. This change accepts that behaviour for the MCP files as it is for the other seeded files. Changing `classify.py` so that a file that already equals the render records the render is possible, is outside this change, and would alter `versions.yaml` and the profile too.
10. **No new dependency; `pyproject.toml` and `uv.lock` are unchanged.**

## Consequences

- Each slice can be reviewed and tested alone, and the security rules exist before anything is written to a client file.
- A maintainer who changes the declaration reviews a diff of the file text, which is the same review that Q-11 asks for.
- Entries do not update by themselves: a new address or variable name always arrives as a proposal. That is slower and visible.
- An invalid declaration blocks the whole `upgrade`. That is deliberate; it is the price of never half-applying a security setting.
- A team's existing MCP file that is untracked, or holds a literal secret, blocks the proposal until it is committed or cleaned, which is the right pressure.
- A recorded MCP file stays in proposal state until Orqlet's classification is changed (decision 9).
- The `shared-entry` mode and the earlier per-entry hash plan (A-31) are not used; the design text is aligned in the document phase.
- The workflow version bump makes this task's own artifacts stale, as the harness2-fit task recorded (`src/orqlet/application/usecases/gate_status.py:179-185`).
- The offline comparison cannot tell a hostile change of both files from a legitimate one; only review can (stated in ADR-002).
- Release 1 is small on purpose: one entry kind for one client. The person can widen it only after the checks.
- The generated Atlassian entry is labelled read-only in the declaration, but the entry restricts nothing; ADR-002 decision 5 and the considerations say so.

## Rejected alternatives

- **Entry-level ownership with JSON and TOML merge.** It needs a TOML round-trip decision that nobody has made and rewrites files that hold team-owned configuration.
- **Orqlet-owned whole files (`generated` ownership with restore).** The classification supports it, but Claude Code's and Cursor's project files are where teams put their own servers, and an owned file would flag or overwrite them.
- **Generators first, validators after.** A generated file would reach users before the rule that rejects a literal credential or a redirected address exists.
- **Leave `doctor` alone.** Seeded files are invisible to its hash checks, so nothing would run the new rules on a developer's machine.
- **Wait for `ci check`.** The offline checks still catch the accidental cases and run in tests today.
- **Write the files for every project.** A project that declares no integration should not get MCP files.
- **Skip the files and write only the instruction.** The standard asks for the same configuration for everyone.
- **Fix the seeded classification in this change.** It reaches files that this task does not own and widens the review.
- **Leave the workflow rule text as it is.** It would tell every agent not to edit a file that teams keep their own servers in.
