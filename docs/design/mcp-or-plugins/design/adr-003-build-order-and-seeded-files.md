# ADR-003: One declaration, one reader, seeded files that never copy the team's text, and the build order

Status: proposed (a design pull request approves it). Task: `mcp-or-plugins`. Reads: AS-IS A-1 to A-17, A-29 to A-34, C-4, C-6; ledger answers Q-11, Q-13; the code of `main` at `e607fe5`.

## Context

- Orqlet writes no MCP file today. The adapters' output sets, the lock and the golden tests contain none (A-1, A-2), `compose` has no MCP step (A-3), the CLI has no MCP command (A-6), and the README says the MCP configuration is not built (A-14, `README.md:38`). The workflow rule text says `.mcp.json` is generated by Orqlet and attaches itself to it (C-4; `src/orqlet/workflow/rules/orqlet-workflow.md:3`, `orqlet-workflow.meta.yaml:10`).
- The contract `orqlet.integrations/v1` exists and nothing reads it (A-8 to A-13). The ownership mode `shared-entry` exists and no adapter sets it (A-4, A-5).
- Since the AS-IS was written, `main` gained a registry of team links with a loader, a validator, a `doctor` hook and a `compose` parameter (`src/orqlet/application/usecases/resources_source.py`, `validate_resources.py`, `diagnose.py:247`, `render_all.py:100-141`). It is the nearest precedent for a declaration that is optional, is read by one function and is checked by `validate` and `doctor`. In that release `init` composes without the registry on purpose, so that a write that stops half-way leaves no generated file that no lock records (`src/orqlet/application/usecases/init_project.py:151-168`), `upgrade` reads it and refuses on an invalid one (`upgrade.py:196-235`), and `explain` previews without it (`explain.py:42-56`). That release also took workflow version 0.3.2 (`src/orqlet/workflow/identity.json`).
- A seeded file that already exists and differs from the render is classified `seeded-proposal` (`src/orqlet/domain/classify.py:65-78`), and a proposal is a unified diff of the existing file against the render, built from the existing bytes at one place, `_propose` (`src/orqlet/domain/changeplan.py:371-381`, `434-443`; called at lines 215 and 265). A proposal for an MCP file would therefore copy the team's existing file, credentials included, into a new file under `.orqlet/proposals`, and nothing in the preview shows that text to the person who approves.
- Once nothing is wanted for a seeded file, the lock forgets it after the next `upgrade` (`classify.py:65-67`, `changeplan.py:337-356`), so the lock cannot be the signal that an MCP file exists.
- The review of this repository is advisory: no `CODEOWNERS`, and branch protection returned HTTP 403 on its plan (`docs/design/open-items/evidence/github-state.yaml:26-31`).

## Decision

1. **Order.** The plan builds in this order and no later step before an earlier one:
   1. the pure module `mcp_credentials` with its negative tests, **already on `main`**;
   2. the contract rules (validators that call `name_problems`), `Integrations.registered_for`, and the update of the valid fixture;
   3. the reader `integrations_source`, `validate_integrations` with the command and `integration_findings`, the hook in `doctor` and `sync`, and `IMPLEMENTED_COMMANDS`;
   4. the guard in the change-plan builder (decision 5), with its `build_plan`-level tests (an existing file with a sentinel, a case variant of the path, the three client paths);
   5. the renderer `render_mcp_file`, `RenderRequest.integrations`, the Claude Code adapter, the `compose` parameter and the call in `upgrade`, with a golden file for the rendered `.mcp.json` and the `upgrade`-level sentinel test of decision 5;
   6. the `.mcp.json` entry in `_OWNED_PATHS` and the words in ORQ-I030;
   7. the protected workflow package: the rule text and its meta file, the manifest rebuild and the version bump together, and the golden files regenerated once;
   8. the documents: the README section for adopters, the corrections of the architecture document, and the repository test that scans the committed check records (ADR-004 decision 1);
   9. the checks of ADR-004 on which the first release's claims depend, by a person, and the README line that says which ones have run;
   10. last, the person runs `orqlet upgrade` in this repository.

   The renderer is not built before the validator that checks its output, and the rule text that says `.mcp.json` is seeded by Orqlet is not shipped before the renderer exists. This change builds and generates **one entry kind**: Atlassian OAuth for Claude Code (ADR-002 decision 2).
2. **The declaration.** `.orqlet/integrations.yaml` is committed, holds no secret and lists servers by identity, purpose, capability tier, expected authentication mode and the clients they are registered for (A-32). It is optional. When it is absent, `upgrade` writes no MCP file. This repository gets none from this change. The contract is tightened in place (Q-13), with the rules of ADR-002 decisions 1, 3, 4, 5 and 10 as validators; the committed JSON Schema does not change (ORQLET-DET-003).
3. **One reader, after the registry's pattern.** The module `integrations_source` has `integrations_path()`, `parse_integrations(loader, raw, source)` and `load_integrations(project, loader, path)`. The result is `(None, ())` for an absent file, `(None, findings)` with at least one error for an invalid one, and `(declaration, findings)` for a valid one, where the findings are information only. The loader owns the three declaration checks: the strict read and the contract validation (including `name_problems`), the closed table (`allowed_auth_modes`) for every server and client it registers, and the scan of the declaration text. It maps each error to a rule id and a closed field name (ADR-002 decision 9). `upgrade` calls it where it calls `load_resources` and passes the declaration to `compose` as one new keyword parameter, `integrations`. A declaration that is present but invalid makes `upgrade` refuse with exit 3 and write nothing, including the other generated files, so that a half-applied security setting never exists; the helper that reads it appends an error finding and returns a refused result before any plan is built, as `_registry` does (`upgrade.py:196-235`). `init` composes without a declaration, as it does without the registry, so the first `.mcp.json` is written by the next `upgrade`; `explain` is not changed. `validate integrations` and `doctor` call the shared function `integration_findings`, so exit 3 and exit 5 come from one reader.
4. **Rendering.** `RenderRequest` gains an optional field `integrations` (default `None`). `compose` sets it with `dataclasses.replace(request, integrations=integrations)` after `build_render_request`, so `render_request.py` and its signature do not change. The field holds the contract object, `Integrations`: ports already import contracts (`src/orqlet/application/ports/scanner.py:8`, `standards.py:8`), the adapter needs exactly `registered_for(client)` and the fields of `McpServer`, and a second small dataclass would repeat them. The Claude Code adapter calls `render_mcp_file(servers, client)` with `Integrations.registered_for(client)` and writes nothing when that is empty; the Codex and Cursor adapters ignore the field in this change. `compose` renders only for clients that the profile enables. The output is one JSON object, `{"mcpServers": {"orqlet-<id>": {"type": "http", "url": "<address>"}}}`, built from `rendered_entry`, with `json.dumps`, an indent of two and a trailing newline (the shape of the vendor's example, `claude-code-mcp.md:36-43`). `render_mcp_file` scans the text it builds and raises if anything is found (ADR-002 decision 7). No timestamp, absolute path or random value (ORQLET-DET-001).
5. **Seeded file, no entry-level editing, and no copy of the team's text.** `.mcp.json` is written as a complete text that holds only the generated entries, with owner `seeded` and no file class. The `shared-entry` mode stays unused and no TOML library is added. A team that deletes the file does not get it back (`classify.py:73`); recreating it is the team's step. The guard sits at the one place where a proposal gets its existing bytes, `_Builder._propose` in `domain/changeplan.py`: when the path is the MCP file of any client (`mcp_file_path` for `claude-code`, `codex` and `cursor`), it passes no existing bytes, whichever branch calls it. The proposal is then a diff against nothing: it shows the text that Orqlet wants and none of the team's file. The guard is derived from the path, not set by an adapter, so a later adapter for `.cursor/mcp.json` or `.codex/config.toml` is covered without remembering anything. Paths are compared on `CanonicalPath.key`, which folds case, so `.MCP.json` is covered on case-insensitive file systems. The places that enumerate the clients are: the private table of paths in `mcp_credentials.py`, the constant of client ids in `changeplan.py`, and the validator's loop over the MCP files; a test fails when they diverge, and a fourth client needs all three. Not covered, and not changed by this design: a profile that names an MCP path as a pull-request template target would make Orqlet write a block into that file, and the backup of that write is a copy in the user data directory; the profile is reviewed like the declaration. `upgrade` prints one information finding for every plan item that is a seeded proposal on an MCP path (it finds them with `mcp_file_path` for the clients in `services.adapters`), saying that the proposal shows only the wanted text and that the team merges it by hand; the code comes from the `ORQ-I53x` family. Nothing depends on the scan, so no credential in an existing file can be copied, whatever its shape; the scan stays in `validate`, `doctor` and `sync`, where it reports and copies nothing. Two effects are accepted: the proposal does not show an old-to-new diff even when Orqlet wrote the file, and a team whose file holds its own servers never equals the render, so its proposal item and its information finding appear on every run until the team merges the wanted text; a proposal file that already holds the same text is not rewritten, so `upgrade --check` finds nothing to write; the README says so. Classification is unchanged, so a re-run, `--resume` and `--check` converge, and an interrupted run (file written, lock not yet) classifies the file as up to date. A test at the `upgrade` level puts a run-time sentinel in an existing `.mcp.json` and asserts that it is absent from every planned write, the preview, the JSON output, the journal and the backups.
6. **Checking.** `orqlet validate integrations [file]` (default `.orqlet/integrations.yaml`) and `integration_findings(project, loader, path)` apply ADR-002 decisions 6 to 10 to the declaration and to the MCP files that exist. `integration_findings` returns findings only. With the declaration absent it returns no finding, or the one warning of ADR-002 decision 11, and it skips unreadable files without a finding; `validate_integrations` does its own existence check, as `validate_resources` does (`validate_resources.py:62`), and is not run (exit 5). An absent MCP file is an information finding; an existing MCP file that lacks a declared entry is an error. `doctor` and `sync` call `integration_findings` from `_diagnose` outside its `full` branch, so both run it; they load the installation like their other checks, so they need an initialised repository, and they check a client's MCP file only if it exists. The command adds `validate integrations` to `IMPLEMENTED_COMMANDS`. New finding codes are in the families `ORQ-E530` to `ORQ-E539`, `ORQ-W530` to `ORQ-W539` and `ORQ-I530` to `ORQ-I539` (unused today), and the plan names each one.
7. **The protected workflow package and the release.** The change touches the package in two files: the rule text `rules/orqlet-workflow.md` and its `rules/orqlet-workflow.meta.yaml`. `.mcp.json` stays in the meta `paths`, so the rule still reaches an agent that edits the file, but the text stops listing it among the generated files and the `description` is reworded to cover both kinds of file. A new bullet says that `.mcp.json` was seeded by Orqlet and belongs to the team afterwards, that `orqlet-*` entries follow the declaration, that changes arrive as proposals, that in a project that holds `.orqlet/integrations.yaml` this release allows no variable reference and no credential value in an `orqlet-*` entry, and that the declaration decides which servers exist; the check runs only in such a project, and the text says so. The contract rules are validators, so the committed schema `orqlet.integrations.v1.json` does not change and `tools/export_schemas.py --check` passes as it is. The manifest is rebuilt (`tools/build_manifest.py --check` runs in CI) and `identity.json` is bumped in the same step (ORQLET-DET-002), so the golden files are regenerated once, on purpose. Version 0.3.2 is already taken, so the proposal is 0.3.3, and the person chooses. Whether and when to record the release in `releases.json` is the person's decision at release time. The approvals of this task become stale (`workflow_version`, `protected_set_digest`, ORQ-W390) when the person runs `orqlet upgrade` here.
8. **Review visibility and documents.** The existing information finding ORQ-I030 lists the paths that a `CODEOWNERS` file should cover; this change adds `.mcp.json` to that list (`_OWNED_PATHS` in `render_all.py`) and the words "the MCP configuration" to its text, so no second finding exists. The finding therefore changes for every project, with or without a declaration, and the tests that pin its list change with it. `.orqlet/integrations.yaml`, `.cursor/mcp.json` and `.codex/config.toml` are already under `.orqlet/**`, `.cursor/**` and `.codex/**`. The README gets a section for adopters: declare, generate, merge a proposal, sign in, take the file over, the CI line, the files that pin the tool, the limits, and which checks have run. The architecture document is aligned with the built contract and rules: the section 24.4 example, the section 15.1 text, the statements that CI validates every MCP entry (T4, T12) and the `shared-entry` and "TOML edited per entry" text of the section 12 note and section 24.7.
9. **The registry of links is a separate thing.** The registry (`.orqlet/resources.yaml`, `docs/resources/**`) holds links to pages and stored copies and has no field in common with the declaration. A link entry never creates an MCP entry and a declaration never creates a link.

## Consequences

- One reader means `doctor`, `validate` and `upgrade` cannot disagree about what is valid.
- `compose` gains a keyword parameter, so its public signature changes (EC-9). `RenderRequest` gains a field that the extractor cannot see (EC-10). The proposal files for the three MCP paths change in content (EC-14).
- A project with no declaration is unchanged in the files it holds. Its `doctor` output changes in two small ways: the ORQ-I030 list, and the warning of ADR-002 decision 11 when an `orqlet-` name is found in an MCP file.
- A team that already keeps its own `.mcp.json` is never rewritten and never copied; it gets a proposal with the wanted text and merges it by hand.
- The Codex and Cursor files and every `env-ref` shape wait for check records (ADR-004); this change adds no code for them.
- The golden files of the three clients change once, through the version bump, and the Claude Code and Cursor ones also through the rule text, which the Codex adapter does not write.
- `init` does not write the MCP file; a first run needs `init` and then `upgrade`, as for the registry's files.
- The comments of `tests/unit/domain/test_mcp_credentials.py` and `test_mcp_credentials_properties.py` cite decisions of the replaced ADRs (ADR-003 decisions 2 and 6, ADR-002 decision 12) with their old meaning; the plan updates them.

## Rejected alternatives

- **A flag on `RenderedFile` and `Desired` that each adapter sets.** It fails open: a new adapter that forgets it copies the team's file. A guard derived from the path fails closed.
- **Scan an existing file and refuse before a proposal is built.** It makes the leak depend on the scan floor, which misses shapes and encodings (ADR-002 decision 7); it blocks unrelated upgrades while the file is merely edited; and it needs a new refusal code and a handler in `upgrade`. Withholding the text needs none of these.
- **Refuse every untracked MCP file in `plan_changes`.** It also refuses the file Orqlet wrote itself before the first commit, so a re-run would not converge.
- **Let `compose` call the loader itself.** Every other input of `compose` is passed in, and the registry set the pattern.
- **Resolve the declaration to a small dataclass in the port.** It would repeat the fields of `McpServer` for no stated need.
- **Edit entries inside a team's file (`shared-entry`).** It needs a TOML round trip for Codex that was never researched (U-53) and puts a rewrite of a team-owned file in the tool.
- **Generate all three clients' files at once.** Cursor and Codex approval, expansion and storage are unknown (U-41, U-47, U-51), and the one entry that is generated has no credential field.
- **A separate command to generate the MCP file.** `upgrade` already is the generator of the other seeded files.
- **A new finding for missing `CODEOWNERS` coverage.** ORQ-I030 already says it.
- **Let the lock signal that an MCP file exists.** The lock forgets a seeded file once nothing is wanted for it.
