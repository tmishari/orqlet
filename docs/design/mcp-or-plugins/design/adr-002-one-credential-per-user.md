# ADR-002: Generated MCP entries carry references only, and Orqlet rejects what it can detect that could hold another user's credential

Status: proposed. It becomes accepted when the design pull request is merged by an authorised person.

## Context

- The standard (Q-6) and the answers (Q-9: no shared identity; Q-10: OAuth sign-in or the user's own personal token) fix what a credential may be: one user's own, obtained by that user.
- What a committed entry may hold. A shared file can name a variable or use a sign-in, and the client reads the user's own value (AS-IS A-61, A-62, A-91, A-110, A-111). Claude Code runs a `headersHelper` that a repository or plugin supplies without the user's credential variables (A-64, A-65), and Codex says its helper command "may be visible to local process inspection; do not embed credentials" (A-93, A-97). Cursor accepts static OAuth client credentials in `mcp.json` (A-113); the Codex command-line option takes a client secret (A-95). Claude Code documents a default form, `${VAR:-default}` (A-62).
- What the built contract allows. `orqlet.integrations/v1` has `AuthSpec.mode` (`client-native-oauth`, `env-ref`, `none`), `env_refs` as free strings, `McpServer.id` and `Registration.name` as free text and `backend_identity` as free text; its base class rejects unknown fields (`common.py:50-53`), but there is no rule on addresses, names or identities (A-8 to A-11). No code reads the contract (A-13), and no code writes, reads or scans an MCP file (A-1, A-2, A-3, A-13).
- What the vendors allow as shared identities. Atlassian supports a service-account API key and a personal token when an administrator enables them, and describes use "on behalf of a shared account" (A-127, A-129, A-130, A-132); whether an administrator can enable one without the other is not stated (AS-IS unknowns under Q-10). The design's own rows list a read-scoped service-account token as a server-enforced read-only identity for developer clients (A-147, A-148, contradiction C-12). Cursor team plugin variables and Team MCP credentials are team-wide (A-114, A-115).
- A variable reference lets a changed entry send the variable's value elsewhere, for example `Authorization: Bearer ${NAME}` pointed at another host (the design's own warning, architecture document line 2552). The pin of such an entry must therefore not come from the same pull request alone.
- Addresses. The GitHub remote server address and its header forms are in the evidence file `github-mcp-server.md:34-63`, an excerpt added during design that the accepted AS-IS does not pin; release 1 does not use it. The Atlassian address `https://mcp.atlassian.com/v2/mcp` is in the vendor's getting-started page (evidence `atlassian-rovo-mcp.md:39-40`) and in A-149; the same page says Claude Code authenticates with `/mcp` (line 43), and names plugin or app routes for Cursor and Codex Desktop (lines 42, 44).
- Whether a project `.codex/config.toml` can hold `mcp_servers` entries is not stated by the vendor text (unknown U-41).
- The team's Atlassian site is `cisco-cxe.atlassian.net`, with Confluence under `/wiki` (the person's answer, Q-14; the link was cut off, so no space or page is known, and whether Jira is on the same site was not stated). The entry's address does not name a site: the Atlassian server is one address for every site, and how a site is chosen at sign-in, and whether a user is limited to one site, are unknown (U-10, U-12).

## Decision

1. **Two ways to authenticate.** A server in the declaration uses `client-native-oauth` (the entry holds no credential field at all) or `env-ref` (the entry names exactly one variable of the user's own, used as `Authorization: Bearer <variable>`). `none` stays in the contract but is not generated. One mode per server for every client of the project; the mode is a project decision reviewed in the pull request. A personal token that needs `Basic`, which Atlassian uses, is not supported (A-129). `backend_identity` is `user-oauth` with `client-native-oauth` and `user-token` with `env-ref`, and nothing else; it is a label that the contract keeps consistent with the mode, not a control, so a declaration with mode `none` has no valid label and is refused. `verification: verified` is refused in this release, because no check record exists that a declaration could point to.
2. **A closed table in the tool, by address, mode and client.** `allowed_auth_modes(url, client)` returns the modes that this release enables for an exact address and a client; any other combination is an error. The table lives outside the contract, so a declaration's validity does not change when a tool release changes the table.
 - **This change enables one row:** `https://mcp.atlassian.com/v2/mcp` with `client-native-oauth` for `claude-code`. Claude Code keeps OAuth sign-ins per endpoint (A-69), and the vendor tells Claude Code users to authenticate with `/mcp` (evidence `atlassian-rovo-mcp.md:43`).
 - **Codex and Cursor OAuth entries** are enabled by a later release that cites the check records V-4 (Codex: whether a project file holds `mcp_servers`, U-41), V-5 and V-10 (where sign-ins are stored and whether a stored token follows an address change; unknown for both, ADR-004).
 - **`env-ref` entries and GitHub** (whose documented route for Claude Code and Cursor is a personal token, A-41, A-152) are enabled per client by a later release that cites the records V-1 to V-4 and V-8 (ADR-004 decision 2).
 - Atlassian stays OAuth-only until V-13 shows whether personal tokens can be enabled without service-account keys.
 - A new server, mode or client needs a tool release, which the repository's own pull request cannot do. That is the independent anchor of the pin, provided the validator runs from reviewed sources (decision 11).
3. **Names.** `id` matches `^[a-z][a-z0-9-]{0,31}$`; the entry is named `orqlet-<id>` and `registration.name` must equal `id`. A variable name matches `^ORQLET_MCP_[A-Z][A-Z0-9]*(_[A-Z][A-Z0-9]*)*$` with at most 48 characters (the prefix keeps it apart from `ORQLET_DATA_DIR`, the one name that Orqlet reads, `wiring.py:43`), and `env-ref` has exactly one. Server ids are unique, and one variable name belongs to one server. Names, values and addresses are ASCII only and nothing is normalised. Every pattern is applied with `fullmatch`, `re.ASCII` and no `IGNORECASE`, and the tests cover a trailing newline and the character U+212A.
4. **Where a reference may appear.** Only as the single header value `Authorization: Bearer ${NAME}` (Claude Code), `Authorization: Bearer ${env:NAME}` (Cursor), or `bearer_token_env_var = "NAME"` (Codex). The default form `:-` is forbidden. The address is a literal: `https`, no user information, query or fragment, no `${`, no backslash or percent-encoding. `command` and `package` contain no `${`. Stdio servers can be declared but cannot be registered for a client in this change.
5. **One source for the entry.** `rendered_entry(server_id, url, variable, client)` is a pure function in the domain module, and `mcp_file_path(client)` gives the path of a client's file. In this change the only combination it builds is Atlassian OAuth for Claude Code; a `variable` or any other client or address is refused as not enabled. The contract's rules on ids, addresses and variable names are **validators** that call `name_problems`, not field patterns, so the committed schema shows the structure only and the patterns stay private to the domain module (precedent: `generated_lock.py:34-44`). The selection of servers for a client is a method of the contract class, `Integrations.registered_for(client)`, which the renderer, the validator and the plan all use; validators in the contract are underscore-named. It builds the mapping of one entry for one client with a closed key set (Claude Code: `type`, `url` and, for `env-ref`, `headers`; Cursor: `url`, `headers`; Codex: `url`, `bearer_token_env_var`), and refuses a combination that the table does not enable. The renderer writes its result and the validator compares it with the file (`entry_differences`), so the pin and the output cannot drift apart; a test renders each shape and validates it, and then mutates each field. The patterns, the table and the key sets are private to the module; `name_problems(server_id, url, variable)` returns rule names for the contract. Forbidden whatever a file says: `headersHelper`, `http_headers_helper`, `envFile`, Cursor's static `auth` block, Codex OAuth client secrets, static header values, and literal values under credential-named keys. A server with `capability_tier` other than `read` cannot have `enforced_by: none` in `registration` or in any `per_client` entry; `clients` must include every client with `register: true`. The labels `registration.mode: read-only` and `write_tools.policy: deny` restrict nothing in the generated entry: the OAuth consent decides the scopes, and release 1 therefore gives the agent the user's full Atlassian permissions (V-13 asks whether scope pins hold).
6. **Entries Orqlet did not generate.** One rule for every committed MCP file. An entry name is compared case-sensitively with the declared names; a name that starts with `orqlet-` in any letter case and is not exactly a declared name counts as an undeclared `orqlet-*` entry. Top-level keys other than `mcpServers` are not examined.

| What an entry holds | Declared entry | Undeclared `orqlet-*` entry | Other undeclared entry |
|---|---|---|---|
| Anything that differs from `rendered_entry` | error | n/a | not examined |
| The entry itself | must be present | error | left alone |
| A key of the closed list: `headersHelper`, `http_headers_helper`, `env_http_headers`, `bearer_token_env_var`, `envFile`, Cursor's `auth` block | only the rendered ones | error | error |
| A `${` anywhere, or a scan finding | error | error | error |
| `command`, `args` or another way to start a process | n/a | error (not rendered) | **left alone, stated limit** |
| A remote address with no reference | must equal the table | error | **left alone** |

 - This closes the cases of an undeclared entry that sends an environment variable to another host or runs a credential helper.
 - Orqlet therefore cannot judge an undeclared entry that starts a process or reaches a server with no reference. That is a stated limit (decision 13): only people reviewing the pull request, and the client's own approval prompt (not relied on until V-1, V-3, V-4), cover it.
 - A team that wants an entry with a variable reference declares it, which needs a table row.
7. **A scan for literals.** `find_literal_credentials(text)` reports line numbers and rule names, never values or raw key names: token-shaped strings (GitHub prefixes `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_` and `github_pat_`, the Atlassian prefix `ATATT`, and `sk-ant-`, `AKIA` and `xox`-style prefixes), a JWT-shaped string, user information in a URL, a credential-named URL query parameter after percent-decoding (the names `key`, `api_key`, `apikey`, `token`, `access_token`, `secret`, `password`, `sig`), an `Authorization`, `Bearer` or `Basic` value that is not the anchored template, and a credential-named key (a key that contains `token`, `secret`, `password`, `passwd`, `apikey`, `api_key`, `private_key` or `authorization`) with a literal value. A key that holds a reference by design (`bearer_token_env_var` with a name that matches the pattern) is exempt. It runs on the raw text and on decoded values (JSON `\u` escapes, TOML escapes, YAML scalars after the loader). Every pattern uses bounded quantifiers (no repetition above 2048) and a prefix anchor, and the scan reads at most 4096 characters per line; a line or a decoded value longer than that is itself a finding (`oversize`) at every call site, so a credential past the cap cannot hide behind it. Its worst case per line is fixed; the worst-case tests use repeated `eyJ` and long runs of one character, a test puts a credential-shaped string at offset 4097 of one line, and the worst-case test fixes a time limit per 4096-character line that the plan sets after a first measurement. The patterns are a floor, not a guarantee. It runs on the declaration, on each rendered text before it is written, on each **planned proposal** of an MCP file before the plan is returned (ADR-003 decision 3), and on each MCP file in `orqlet validate integrations`, `doctor` and `sync`.
8. **Parsing is strict and bounded.** The declaration and an MCP file are refused above 256 KiB (the check follows the port's read, so it bounds the parse and the scan, not the read), nesting above 16 levels, 64 entries, or a string above 2048 characters. JSON is read with duplicate keys rejected; TOML with the standard library (which rejects duplicates). `json.JSONDecodeError`, `tomllib.TOMLDecodeError`, `UnicodeDecodeError`, `RecursionError`, `OverflowError` and `ValueError` are each turned into a finding. Valid input of the wrong shape (the top level, `mcpServers` or an entry that is not an object) is a finding, not an exception. A link, a directory or an unreadable file (`LinkRefused`, `NotARegularFile`, `PathNotFound` on a path that was listed) is a finding `unreadable` for that file and does not abort the other checks. Any other exception is a defect and exits 70 with no message text. Files are untrusted input (ORQLET-SEC-002) and are never evaluated.
9. **Messages never carry a value or a raw key.** `load_integrations` does not use the default error text of the contract loader, which prints `loc` and `msg` (and so raw keys of free-form maps), and it catches `DocumentError` from the strict YAML loader, whose text can hold a duplicate key or a tag. It maps each contract error to a rule id and a closed field name, prints `<key>` for a key of a free-form map and `unknown-key` for an unknown field (the contract's `extra="forbid"` otherwise puts the raw key in the error location), and prints for an unreadable declaration only the rule `declaration-unreadable`. The JSON reader for MCP files raises a rule `duplicate-key` and no key text. These two findings carry no line number, because the strict YAML loader and the standard-library JSON hook give no position. `entry_differences` names fields from a closed vocabulary (`type`, `url`, `headers`, `bearer_token_env_var`, `entry`, `unknown-key`) and never an unknown key or an undeclared name. No custom validator formats a value. Findings from decoded values carry the closed field name instead of a line number. Tests put a credential-shaped string in a key and in a value of each free-form map and require that no output holds it.
10. **Committed assignments** (specified here, built by the release that enables `env-ref`, because a declared variable cannot exist before). `validate integrations` reports an assignment of a declared variable name in a closed list of tracked files, read as committed content through the `Vcs` port (`read_committed`): `.claude/settings.json`, `.envrc`, `.env` and `.devcontainer/devcontainer.json`. Such a committed file would hand the same value to everyone. The same caps apply (256 KiB, 4096 characters per line), the parse is line-based and never echoes content, and a failure is reported as a check that did not run. Personal files (`.claude/settings.local.json`, an untracked `.env`) are never read, and no value is printed.
11. **Who runs the check, and what it depends on.** `orqlet doctor` and `orqlet sync` (which share one diagnosis) run the same checks whenever a declaration exists. The README tells adopters to add `orqlet validate integrations .orqlet/integrations.yaml` to their CI, with the tool installed at a pinned version from a reviewed source, until `ci check` exists, and says that only this command checks the rules (the committed JSON Schema does not express them). `validate integrations` returns not run (exit 5) when the declaration is absent, and `doctor` and `sync` report a check that did not run when the lock records an MCP file but no declaration exists. `doctor` also prints an information finding, in the pattern of ORQ-I030, when no `CODEOWNERS` file mentions these paths (a substring test; comments, ownerless lines and which file GitHub reads are not examined, so the finding states a mention, not an effective review): the declaration, the MCP files, `.github/workflows/**`, `.orqlet/versions.yaml`, `.claude/settings.json` and `CODEOWNERS` itself. The pin is independent of the declaration only if the validator runs from reviewed sources: a pull request that edits the workflow that runs it, the pinned tool version, `.claude/settings.json` or `CODEOWNERS` can switch the check off, and so can deleting the declaration. Without a required review and a required status check on the host, this control is advisory.

13. **What Orqlet can and cannot promise.**
 - *Same configuration for everyone*: generated from one declaration; **detectable on demand** (the command, `doctor`, the adopter's CI line). The seeded files are written only when absent and later changes arrive as proposals, so a file edited by hand stays as edited until the check is run. Not covered: a personal same-name entry.
 - *Each user's own credential*: for what the repository holds, the declaration cannot name a shared identity and no committed file may hold a credential; both are **detectable on demand**, and the literal scan can miss a shape it does not know. For the user's side (their own sign-in, their own variable, a fine-grained read-only token for GitHub), the design provides an **instruction** in the README, not a check.
 - *Never another user's credential*: **not enforceable** by Orqlet. A person can lend a token or a shell. Routes that Orqlet cannot close and does not examine: managed MCP configuration that an administrator sets for every user (Claude Code, A-67) and Codex cloud-managed configuration (A-104, A-106); plugins and marketplaces that a committed `.claude/settings.json` enables (A-85, A-87) and plugin settings in a project `.codex/config.toml` (A-103); other keys of the Codex file; an undeclared entry that starts a process or reaches a server without a reference (decision 6); committed assignments outside the closed list of decision 10; and an environment of a cloud agent, a review context or CI that several people share.
 - Also not examined: an undeclared entry in `.cursor/mcp.json` or `.codex/config.toml` whose name equals a personal entry, because Cursor merges the project and global files (A-109) and Codex project settings override user settings (A-104), and whether a merge is per field is not stated; committed hooks, `env` or helper commands in `.claude/settings.json`, which can read user variables or the OAuth store (A-74); inline servers in agent files, which Claude Code can load from a project (`.claude/agents/*`; A-65, A-66) and whether `${VAR}` expands there; MCP files in nested or parent folders (V-7); and any project that has no declaration, where no check runs (this repository has none).
 - *Unattended surfaces*: the person's answer to Q-12 is that an unattended surface uses the account of the one user who started or owns it; V-12 checks whether the clients can do that. Where they cannot, or where the environment is shared by several people, Q-6 and Q-9 are not met for **every mode, OAuth included** on cloud agents, review contexts and CI, because whichever identity such a surface holds serves everyone who triggers it (the vendor itself markets API-token use for CI and bots, evidence `atlassian-rovo-mcp.md:10,23,31`; A-127).
 - One variable per server is read by all three clients, so the user's own value is used in each; Orqlet copies nothing between clients (A-37, A-44), and the sharing of one value among clients is the user's choice.

## Consequences

- `orqlet validate integrations` becomes the check of the standard and `doctor` and `sync` surface it. `validate integrations`, `doctor` and `sync` exit 5 on any rule above; `init`, `upgrade` and `explain` refuse with exit 3 on an invalid declaration (ADR-003). Output holds rule names, line numbers and closed-vocabulary field names, never a value or a raw key.
- **The contract is tightened in place.** The architecture document's versioning rule says a breaking change of a schema is major and ships a migration (Section 20.2, line 4055). Tightening `orqlet.integrations/v1` can make a hand-written declaration invalid. In this repository no module reads the contract and no declaration exists (A-13); whether any other project holds one is not known, and a declaration has no effect today. The person decided on 2026-10-26 to tighten v1 in place and not to add `orqlet.integrations/v2` (Q-13). The existing valid fixture `tests/fixtures/contracts/valid/orqlet.integrations.v1.yaml` (`docs.example.com`, `backend_identity: Example`) would fail the new rules and is updated in phase 2 together with its tests; the committed JSON Schema does not change.
- The architecture document's Section 24.4 example is aligned with the built contract (contradiction C-6), and its Section 15.1 text (variables allowed in `url` and `env`, doctor reporting duplicates) is aligned with these rules.
- The `variable` parameters of `rendered_entry` and `name_problems` and the function `referenced_variables` exist now so that the public signatures do not change when `env-ref` is enabled; in release 1 `rendered_entry` refuses a variable, and `referenced_variables` is used on undeclared entries (decision 6).
- The first release generates one entry kind: Atlassian OAuth for Claude Code. The `env-ref` shapes, the Codex and Cursor shapes and GitHub are specified here and built, with their tests, by the release that enables them, so no code path ships that cannot run. A project cannot declare a server whose address is not in the table, nor a shared read-only Atlassian identity. If Q-9 is answered differently or a new server is wanted, a new design and a tool release follow.
- A GitHub entry in `env-ref` mode will need every developer to create a PAT. The user who does not set the variable gets a failed or unauthenticated connection (Codex states the second, A-94; the other clients are recorded in V-2 and V-3).
- A GitHub personal token with write scopes is not limited by the entry: the server filters nothing for "other tokens" (evidence `github-mcp-server.md:27`). The README instruction names a fine-grained read-only token.
- The scan can miss a credential shape it does not know, which is why the pin comparison, the closed key sets, the declared-only rule and review exist as well.
- A team's own entry that uses a variable reference is an error until it is declared (decision 6). That is strict and deliberate.
- New code: seven pure functions and one class in one pure module, one loader, one use case, one renderer and one CLI subcommand (the component view).

## Rejected alternatives

- **Allow `headersHelper` and `http_headers_helper`.** They run a command from a repository file, and the clients treat them as untrusted code (A-64, A-97).
- **Allow `${VAR}` in `url` or `env`.** It would let a variable steer the address; the address must stay a literal that the pin can compare.
- **Any https address, pinned by the declaration alone.** The declaration is in the same pull request as the file, so the pin would have no independent anchor.
- **Put the address table in the contract.** A declaration's validity would then change with a tool release.
- **Flag every undeclared entry.** Teams keep their own servers in these files (ADR-003); an error on each would make the command unusable for them. The narrower rule of decision 6 closes the exfiltration of a variable and states the remaining limit.
- **Put the rules in the JSON Schema.** It would need patterns that exist twice and would let the schema and the domain drift.
- **Support `Basic` for Atlassian personal tokens now.** The header cannot be written as a Bearer template and the enablement question is open (V-13).
- **Write the credential into the file with a warning.** It breaks ORQLET-SEC-003 and the standard.
- **A service account for read-only Atlassian use.** Q-9 refuses a shared identity.
- **Detect lending of tokens by comparing identities at the server.** Orqlet reads no server and no credential store; the vendor's audit log is the only place where that is visible.
- **Bump the contract to a new identifier now.** Nothing in this repository reads it, and the person chose not to (Q-13).
- **Build all three client shapes and the `env-ref` form now.** They could not run in this release and could not be tested end to end.
