# ADR-002: Entries carry references only; each user brings their own credential

Status: proposed (a design pull request approves it). Task: `mcp-or-plugins`. Reads: AS-IS facts and unknowns, ledger answers Q-6, Q-9, Q-10, Q-12, Q-13, Q-14.

The pure module `src/orqlet/domain/mcp_credentials.py` already exists on `main` (commit `e607fe5`, phase P-1 of the plan that this design replaces). Its comments cite decisions 2, 3, 4, 6, 7, 8 and 9 of this ADR by number, so those numbers are kept here. This design keeps the module and its eight public names unchanged. Where a decision below is stronger than the module, the decision says which part is built elsewhere.

## Context

- The standard (Q-6) and the answers (Q-9: no shared identity; Q-10: OAuth sign-in or the user's own personal token) fix what a credential may be: one user's own, obtained by that user.
- What a committed entry may hold. A shared file can name a variable or rely on a sign-in, and the client reads the user's own value (A-61, A-62, A-91, A-110, A-111). Claude Code runs a `headersHelper` that a repository or plugin supplies without the user's credential variables (A-64, A-65), and Codex says its helper command "may be visible to local process inspection; do not embed credentials" (A-93, A-97). Cursor accepts static OAuth client credentials in `mcp.json`, and the names of those fields are not in the evidence (A-113, U-48). The Codex command line takes a client secret (A-95). Claude Code documents a default form `${VAR:-default}` (A-62).
- What the built contract allows. `orqlet.integrations/v1` has `AuthSpec.mode`, `env_refs` as free strings, `McpServer.id`, `Registration.name` and `backend_identity` as free text; its base class rejects unknown fields, but nothing limits addresses, names or identities (A-8 to A-11). The contract also forces `registration.mode` to `read-only` and `write_tools.policy` to `deny` (`src/orqlet/application/contracts/integrations.py:21-24`, `36-38`). No module reads the contract and none writes, reads or scans an MCP file (A-1, A-2, A-3, A-13).
- Shared identities that vendors offer. Atlassian supports a service-account key and a personal API token when an administrator enables them, and describes use "on behalf of a shared account" (A-127, A-129, A-130, A-132). Cursor team plugin variables and Team MCP credentials are team-wide (A-114, A-115). The proposal's own rows list a read-scoped service-account token for developer clients (A-147, A-148, C-12, C-13).
- A variable reference lets a changed entry send the variable's value elsewhere, for example `Authorization: Bearer ${NAME}` aimed at another host (the proposal's own warning, A-34). The pin of such an entry must not come from the same pull request alone.
- The Atlassian address `https://mcp.atlassian.com/v2/mcp` is on the vendor's getting-started page, which also says that Claude Code authenticates with `/mcp` (evidence `atlassian-rovo-mcp.md:39-43`; A-149).
- The team's own Atlassian site is in the person's answer Q-14. The entry's address does not name a site, because the Atlassian server is one address; how a site is chosen at sign-in, and whether a user is limited to one site, are unknown (U-10, U-12).

## Decision

1. **Two ways to authenticate.** A server in the declaration uses `client-native-oauth` (the entry holds no credential field) or `env-ref` (the entry names exactly one variable of the user's own, used as `Authorization: Bearer <variable>`). `none` stays in the contract type but is refused for a registered server. There is one mode per server for every client of the project, and the mode is a project decision reviewed in the pull request. A personal token that needs `Basic`, which Atlassian uses (A-129), is not supported. `backend_identity` is `user-oauth` with `client-native-oauth` and `user-token` with `env-ref`, and nothing else. It is a label that the contract keeps consistent with the mode, not a control. `verification: verified` is refused, because no check record exists that a declaration could point to. The `env-ref` rules are specified here so that the contract does not change again; this change builds no `env-ref` entry.
2. **A closed table in the tool, by address, mode and client.** `allowed_auth_modes(url, client)` returns the modes that this release enables for an exact address and a client, and any other combination is an error. The table lives in the domain module, outside the contract, so the contract's own rules do not change when a tool release changes the table; a declaration that names a combination which a later table no longer enables is refused by the loader, with a rule that says so. This change enables one row: `https://mcp.atlassian.com/v2/mcp` with `client-native-oauth` for `claude-code`. Claude Code keeps OAuth sign-ins per endpoint (A-69), and the vendor tells Claude Code users to authenticate with `/mcp` (`atlassian-rovo-mcp.md:43`). Every other row waits for a later release that cites check records (ADR-004 decision 2). A new server, mode or client therefore needs a tool release, which the adopter's own pull request cannot make; that is the independent anchor of the pin, provided the validator runs from reviewed sources (decision 11).

   | Server | Modes in this change | Facts |
   |---|---|---|
   | Atlassian Rovo (Jira and Confluence, one entry) | `client-native-oauth` for Claude Code | OAuth 2.1 is the default and every action respects the user's permissions (A-126, A-128, A-131). The service-account key is the shared identity that Q-9 refuses (A-130, A-132). A personal token needs `Basic` and an administrator's enablement (A-127, A-129) |
   | GitHub remote | none; no GitHub entry and no GitHub address in the table | The documented route for Claude Code and Cursor is a personal token, second-hand for Cursor (A-41, A-143, A-152). OAuth is recommended "if your client application supports" it, and no supported client is named (A-122, U-9). A token other than a classic PAT is not filtered by the server (`github-mcp-server.md:27`). A GitHub row waits for checks V-1, V-2, V-7, V-8, V-9 and V-10 |
   | Miro | none | ADR-001 decision 5 |
3. **Names.** A server `id` matches `^[a-z][a-z0-9-]{0,31}$`; the entry is named `orqlet-<id>`, and `registration.name` equals `orqlet-<id>`. A variable name matches `^ORQLET_MCP_[A-Z][A-Z0-9]*(_[A-Z][A-Z0-9]*)*$` with at most 48 characters, so it stays apart from `ORQLET_DATA_DIR`, the one variable that Orqlet reads. An `env-ref` server has exactly one variable and an OAuth server none. Server ids are unique and one variable name belongs to one server. Names, values and addresses are ASCII only and nothing is normalised. Every pattern is applied with `fullmatch`, `re.ASCII` and no `IGNORECASE`, and the tests cover a trailing newline and the character U+212A.
4. **Where a reference may appear.** Only as the single header value `Authorization: Bearer ${NAME}` (Claude Code), `Authorization: Bearer ${env:NAME}` (Cursor) or `bearer_token_env_var = "NAME"` (Codex), and only for a row that a later release enables. The default form `:-` is forbidden. The address is a literal: `https`, a host, an optional port and an optional path of ASCII path characters; no user information, query or fragment, no `${`, no backslash and no percent-encoding. `command` and `package` contain no `${`. A stdio server can be declared, but it cannot be registered for a client in this change.
5. **One source for the entry.** `rendered_entry(server_id, url, variable, client)` builds the entry, and `mcp_file_path(client)` gives the path of a client's file. Both are pure functions in the domain module. The renderer writes what `rendered_entry` returns and the validator compares a file with it through `entry_differences`, so the pin and the output cannot drift apart. In this change the only combination built is Atlassian OAuth for Claude Code, `{"type": "http", "url": <address>}`; a variable or any other client or address is refused. The contract's rules on ids, addresses and variable names are validators that call `name_problems`, not field patterns, so the committed JSON Schema does not change and the patterns stay private to the domain module (precedent: the model validator at `src/orqlet/application/contracts/generated_lock.py:34-47`; the validators are named with a leading underscore). The validators call `name_problems(server_id, url, variable)` and map the rule names that it returns (`server-id-pattern`, `variable-pattern`, `variable-length`, `address-literal-https`) to closed field names; a stdio server has no address, so for it the validator passes an empty address and drops `address-literal-https` from the result. `Integrations.registered_for(client)` returns the servers whose `per_client[client].register` is true, in declaration order. The set of names that a file may hold as declared entries is exactly `orqlet-<id>` of those servers. When no server is registered for a client, no file is written for it, not an empty one. Whether the table enables a server for a client is checked by the loader (ADR-003 decision 3) before `rendered_entry` is called, so `rendered_entry` never meets an unenabled combination in normal use; its refusal is the second guard.
6. **What the validator does with each entry.** The validator reads JSON MCP files (`.mcp.json`, `.cursor/mcp.json`). A name is compared case-sensitively with the declared names, and a name that starts with `orqlet-` in any letter case and is not exactly a declared name is an undeclared `orqlet-*` entry. Top-level keys other than `mcpServers` are not examined. After a successful parse the validator walks the whole parsed document, entry names and top-level keys included, and every decoded key and string value at any depth, and applies the closed-key test and the `${` test to the decoded text, so a JSON escape such as `\u0024{` or `Author\u0069zation` changes nothing. The closed key list is a private constant of `validate_integrations.py`; it holds the key names that the evidence gives: `headersHelper` (A-64), and `http_headers_helper`, `env_http_headers` and `bearer_token_env_var` (A-91 to A-93), compared case-insensitively. Names the evidence does not give, such as Cursor's static OAuth fields (U-48), are not listed; a check record adds them when it exists.

   | What the validator finds | Result |
   |---|---|
   | A declared entry that differs from `rendered_entry` in a field | error, naming fields from a closed vocabulary |
   | A declared entry that is absent from a file that exists | error |
   | An undeclared `orqlet-*` entry | error |
   | Any entry with a key of the closed list, or whose text holds the substring `${` | error |
   | Any file or decoded string with a scan finding (decision 7) | error |
   | Another undeclared entry with none of the above | left alone, and counted |

   The validator prints one information finding with two counts, never names: the undeclared entries, and those among them whose `url` has no enabled mode for the client. A reviewer who sees `3 undeclared, 3 off the table` knows that the pin covers nothing for them. For `.codex/config.toml` the validator runs the scan only, because no row generates it and a TOML reader would add a second parser path and a decoded scan for a file that Orqlet does not write; `tomllib` is in the standard library and the scanners already use it, so this is a choice of scope, not of dependency (ADR-003 decision 5 adds no TOML library). Orqlet therefore cannot judge an undeclared entry that starts a process or reaches a server without a reference, nor the Codex helper and static-credential keys; those are stated limits (decision 12). Only the people who review the pull request, and the client's own approval prompt (not relied on until V-1), cover them. A team that wants an entry with a variable reference declares it, which needs a table row.
7. **A scan for literals.** `find_literal_credentials(text)` reports line numbers and rule names, never values or raw key names. What it covers is the floor that the module implements: token-shaped strings with the prefixes `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `ATATT`, `sk-ant-`, `AKIA` and `xox[abprs]-` (the `ATATT` shape is not from the vendor evidence and is unverified, and the shape of an Atlassian service-account key is unknown, so the scan is not claimed to cover it); a JWT-shaped string; user information in a URL; a URL query parameter named `key`, `api_key`, `apikey`, `token`, `access_token`, `secret`, `password` or `sig` after percent-decoding; an `Authorization`, `Bearer` or `Basic` value that is not the anchored template; and a key containing `token`, `secret`, `password`, `passwd`, `apikey`, `api_key`, `private_key` or `authorization` with a literal value. A token that follows a letter, digit or underscore is not matched; the Bearer and Basic rule needs a digit, `=`, `+` or `/` in the value, so a token made of letters only is found only when its key is credential-named; and query parameters are split on `&` only. Every pattern has bounded quantifiers and a prefix anchor, the scan reads at most 4096 characters per line, and a longer line is itself a finding (`oversize`). **The scan reads text, so an encoded credential can slip past it:** a JSON escape inside a token prefix or key name, or a TOML line continuation, changes the text that the patterns see. For that reason the validator scans the raw text of a file and, for a JSON file that parses, a second text as well: a re-serialisation of the whole parsed document with every decoded key and value on its own line (`json.dumps(document, ensure_ascii=False, indent=1)`), so that the key rules and the `Authorization` rule see a key and its value together. A finding on that text names the rule and the word `decoded`, with no line and no key. Whether a client expands `\u0024{` as a variable reference is not known (V-9). The TOML file gets the raw scan only; that leaves TOML `\u` and `\U` escapes, escaped quoted keys and a line continuation unscanned, and percent-encoding inside a URL path or value is not decoded either. A test uses a lone surrogate (`\ud800`) in a JSON string. The patterns are a floor, not a guarantee, and the module may be extended by a later phase. The scan runs on the declaration (in the loader), on each rendered text before it is written, and on each MCP file in `orqlet validate integrations`, `doctor` and `sync`. The scan of a rendered text runs inside `render_mcp_file`: the entry has no credential field, so a finding there is a defect, `render_mcp_file` raises, and the run exits 70 with nothing written.
8. **Parsing is strict and bounded.** The declaration and an MCP file are refused above 256 KiB (the same cap as the registry of links, `src/orqlet/application/usecases/resources_source.py:23`), nesting above 16 levels, 64 entries, or a string above 2048 characters; the three small limits keep the cost of one parse fixed. The port has no bounded read, so the size is checked after the file is read; the files are small and the read is the same whole-file read that `plan_changes` already does. JSON is read with duplicate keys rejected. `json.JSONDecodeError`, `UnicodeDecodeError`, `RecursionError`, `OverflowError` and `ValueError` are each turned into a finding. Valid input of the wrong shape (the top level, `mcpServers` or an entry that is not an object) is a finding, not an exception. When a declaration exists, a link, a directory, an unreadable file or a file that is not valid UTF-8 is an `unreadable` **error** for that file (exit 5) and does not stop the other checks; a link must not hide an entry from the validator while a client may follow it. Every file-system error is caught for the one file, including a link in a parent folder. When the declaration is absent, such a file produces one information finding, which does not change the exit code, and nothing is checked in it, because a project without a declaration keeps its behaviour; tests cover a symlinked `.mcp.json`, a symlinked parent folder, a file over the cap and a file that is not UTF-8, in each branch. When a declaration registers Claude Code and `.mcp.json` is a link or not a regular file, `plan_changes` already refuses with `ORQ-E114` and `upgrade` exits 3 before anything is written (`render_all.py:367`). Any other exception is a defect and exits 70 with no message text. Files are untrusted input (ORQLET-SEC-002) and are never evaluated.
9. **Messages never carry a value or a raw key.** The loader does not use the default error text of the contract loader, which prints `loc` and `msg` (so raw keys of free-form maps), and it catches `DocumentError` from the strict YAML loader, whose text can hold a duplicate key or a tag. It maps each contract error to a rule id and a closed field name, prints `<key>` for a key of a free-form map and `unknown-key` for an unknown field, and prints for an unreadable declaration only the rule `declaration-unreadable`. The JSON reader raises a rule `duplicate-key` and no key text. These two findings carry no line number, because the strict YAML loader and the standard-library JSON hook give no position. `entry_differences` names fields from a closed vocabulary (`type`, `url`, `headers`, `bearer_token_env_var`, `unknown-key`) and never an unknown key or an undeclared name. No custom validator formats a value. Tests put a credential-shaped string in a key and in a value of each free-form map and require that no output holds it; the escaped shapes of decision 7 are assembled at run time, never written out (ORQLET-SEC-003).
10. **Labels that say only what holds.** The contract forces `registration.mode: read-only` and `write_tools.policy: deny` on every declaration (`Literal` values), and the generated entry restricts nothing: the OAuth consent decides the scopes, so the agent gets the user's Atlassian permissions (A-126, A-128). The contract therefore refuses `enforced_by: server` in `registration` and in every `per_client` entry, because no row of the table has a server-side limit; a server with a `capability_tier` other than `read` cannot have `enforced_by: none` anywhere; and `clients` must include every client with `register: true`. The two forced labels stay, as a known limit that this design does not remove: they are `Literal` values of the contract, so changing them is a schema change (ORQLET-DET-003) that Q-13 did not cover and that is the person's decision (open point), and `validate integrations` and `doctor` print one information finding for each registered OAuth server that says the entry gives the user's full permissions.
11. **Who runs the check, and what it depends on.** `orqlet validate integrations` returns not run (exit 5) when the declaration is absent. It works without an installed profile; it reads only the declaration and the MCP files. `orqlet doctor` and `orqlet sync` run `integration_findings` like their other checks, so they need an initialised repository. When the declaration is absent and an MCP file of any client holds the text `orqlet-` in any letter case, or, when the file parses as JSON, a decoded entry name that starts with `orqlet-`, `doctor` and `sync` print a warning that says nothing was checked and why; the signal does not depend on the lock, which forgets a seeded file once nothing is wanted for it. A warning makes `doctor` exit 1, like the other warnings. So deleting the declaration is visible while an `orqlet-` name remains, but it is not blocked; a team that takes the file over renames or removes the `orqlet-*` entries, and the README says so. A pull request that deletes the declaration and renames the entries in the same change leaves `doctor` and `sync` silent: that is a stated limit, and only review covers it. The README names the files that pin the tool (the version in the CI workflow and any lockfile) and tells adopters to add `orqlet validate integrations .orqlet/integrations.yaml` to their CI with the tool installed at a pinned version from a reviewed source, until `ci check` exists, and says that only this command checks the rules (the committed JSON Schema does not express them). The pin is independent of the declaration only if the validator runs from reviewed sources: a pull request that edits the workflow that runs the check, the pinned tool version, `.claude/settings.json` or `CODEOWNERS` can switch the check off. Without a required review and a required status check on the host the control is advisory. This repository has no `CODEOWNERS`, and branch protection returned HTTP 403 on its plan (`docs/design/open-items/evidence/github-state.yaml:26-31`).
12. **What Orqlet can and cannot promise.**
    - *What Orqlet reads:* it never reads a credential store and its own output never carries a credential value. It does read repository files that may hold a pasted credential, in order to scan them, and it reports only rule names and positions. One existing behaviour is outside this design: `orqlet review prepare` copies the files of the staged tree into a packet outside the repository without a scan, so a staged MCP file with a pasted credential would be copied there (an open point).
    - *Same configuration for everyone:* generated from one declaration and **detectable on demand** (the command, `doctor`, the adopter's CI line). The seeded file is written when absent and later changes arrive as proposals, so a file edited by hand stays as edited until the check is run. Not covered: a personal same-name entry (V-4).
    - *Each user's own credential:* for what the repository holds, the declaration cannot name a shared identity and no committed file may hold a credential. Both are **detectable on demand**, and the scan can miss a shape it does not know or a credential that someone encoded on purpose. A shared Atlassian account that a human signs in to cannot be told apart from a personal one. For the user's side (their own sign-in, their own variable, a fine-grained read-only token for GitHub) the README gives an **instruction**, not a check.
    - *Never another user's credential:* **not enforceable** by Orqlet. A person can lend a token or a shell. Routes that Orqlet does not examine: managed MCP configuration that an administrator sets for every user (Claude Code, A-67) and Codex cloud-managed configuration (A-104, A-106); plugins and marketplaces that a committed `.claude/settings.json` enables (A-85, A-87) and plugin settings in a project `.codex/config.toml` (A-103); other keys of the Codex file, including its helper and static-credential keys; an undeclared entry that starts a process or reaches a server without a reference (decision 6); committed hooks, `env` or helper commands in `.claude/settings.json`, which can read user variables or the OAuth store (A-74); inline servers in agent files (A-65, A-66); a committed project settings file that pre-approves project MCP servers (not in the evidence, asked in V-1); MCP files in nested or parent folders (V-6); and a project that has no declaration, where no check runs (this repository has none).
    - *Unattended surfaces:* the person's answer to Q-12 is that an unattended surface uses the account of the one user who started or owns it. Check V-10 asks whether the clients can do that. Where they cannot, or where one environment is shared by several people, Q-6 and Q-9 are not met for **every mode, OAuth included**, on cloud agents, review contexts and CI, because whichever identity such a surface holds serves everyone who triggers it (the vendor itself offers API-token use for CI and bots, `atlassian-rovo-mcp.md:10,23,31`; A-127).
    - *Reach of the entry:* an OAuth entry that carries the user's full permissions lets text that the agent reads through the server (an issue, a page) steer actions with the user's write rights. The entry does not limit that, and V-10 asks whether a client can request fewer scopes (A-146). Until it is answered the README says so.
    - *Reach of this change:* the standard is met by what Orqlet generates only for Atlassian on Claude Code. GitHub, Miro, Cursor and Codex stay manual and unverified; the README says so plainly.
    - One variable per server is read by all three clients when an `env-ref` row exists, so the user's own value is used in each; Orqlet copies nothing between clients (A-37, A-44), and sharing one value among clients is the user's choice.

## Consequences

- `orqlet validate integrations` becomes the check of the standard, and `doctor` and `sync` surface it. They exit 5 on any error above; `upgrade` refuses with exit 3 on an invalid declaration (ADR-003). Output holds rule names, line numbers and closed-vocabulary field names, never a value or a raw key.
- **The contract is tightened in place.** The architecture document says a breaking change of a schema is major and ships a migration (section 20.2). Tightening `orqlet.integrations/v1` can make a hand-written declaration invalid. In this repository no module reads the contract and no declaration exists (A-13); whether another project holds one is not known, and a declaration has no effect today. The person decided on 2026-10-26 to tighten v1 in place and not to add `orqlet.integrations/v2` (Q-13). A team with a hand-written declaration that breaks the new rules gets a refusal from `upgrade` until it is fixed. The valid fixture `tests/fixtures/contracts/valid/orqlet.integrations.v1.yaml` (`docs.example.com`, `backend_identity: Example`, `enforced_by: server`) fails the new rules and is updated with its tests; the committed JSON Schema does not change.
- An adopter's existing entry with a `${VAR}` reference or an `Authorization` line turns `validate integrations` red, because this release has no row that could declare it. That is strict and deliberate (decision 6).
- The proposal's section 24.4 example is aligned with the built contract (C-6) and its section 15.1 text (variables allowed in `url` and `env`) is aligned with decisions 3 to 5.
- The `variable` parameters of `rendered_entry` and `name_problems` and the function `referenced_variables` exist so that the public signatures do not change when `env-ref` is enabled. `rendered_entry` refuses a variable now, and `referenced_variables` is used on entries that the validator reads.
- The first release generates one entry kind. The `env-ref` shapes, the Cursor and Codex shapes and GitHub are specified here and built, with their tests, by the release that enables them, so no code path ships that cannot run.
- A GitHub entry in `env-ref` mode will need every developer to create a token. A user who does not set the variable gets a failed or an unauthenticated connection (Codex says the second, A-94; the other clients are check V-2).
- A GitHub personal token with write scopes is not limited by the entry (`github-mcp-server.md:27`). The README instruction will name a fine-grained read-only token.
- The scan can miss a credential shape it does not know, which is why the pin comparison, the closed key list, the declared-only rule and review all exist.

## Rejected alternatives

- **Allow `headersHelper` and `http_headers_helper`.** They run a command from a repository file, and the clients treat them as untrusted code (A-64, A-97).
- **Allow `${VAR}` in `url` or `env`.** A variable could steer the address; the address must stay a literal that the pin can compare.
- **Any https address, pinned by the declaration alone.** The declaration is in the same pull request as the file, so the pin would have no independent anchor.
- **Put the address table in the contract.** A declaration's validity would then change with a tool release.
- **Flag every undeclared entry.** Teams keep their own servers in these files; an error on each would make the command unusable for them. The narrower rule of decision 6 closes the exfiltration of a variable and the counts show the rest.
- **Put the rules in the JSON Schema.** The patterns would exist twice and the schema and the domain could drift.
- **Support `Basic` for Atlassian personal tokens now.** The header cannot be written as a Bearer template and the enablement question is open (U-74).
- **Write the credential into the file with a warning.** It breaks ORQLET-SEC-003 and the standard.
- **A service account for read-only Atlassian use.** Q-9 refuses a shared identity.
- **Detect lending of tokens by comparing identities at the server.** Orqlet reads no server and no credential store (A-53).
- **A TOML reader for the Codex file now.** It is new code for a file that no row generates.
